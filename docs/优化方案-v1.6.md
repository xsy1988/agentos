## §1 结论摘要

### 1.1 三句话结论

1. 原方案**方向正确、事实有误**：平台并不缺"等待能力"的机制（`interrupt` + PG 检查点 + `inbox_events` 恢复 + 支线收敛**都已存在且在用**），真正的断裂点是**"全局超时"没有账本**——`runs.started_at` 一个字段都没写过，超时计时按"段"重置，导致一次 1401 秒的执行在最后 600 秒被判死、`result=NULL`、全部成果丢弃 `[实测][代码]`。
2. 平台的**能力可见性缺陷被原方案低估**：`tool_budget` 只有 8 和 6，而单个 `filesystem` MCP 就展开 **14** 个工具，装配末尾是**硬切片** `tools[:tool_budget]` `[实测][代码]`——这不是"可能不进列表"，而是**结构性算术超约束**，Worker 声明的核心工具必然被截断。
3. v1.6 的主线是**三件事**：让运行时长可测且超时真正全局（P0-1）、让能力可见性成为硬保证（P0-2）、让失败与结果成为结构化一等对象（P0-3/P0-5）。await 一等化（P0-4）与 inbox 契约闭合（P0-6）是随之的必要配套。

### 2.2 单 run 尸检：`47d69dcc-8880-4848-860b-ab6e7d84d802`

这是 Q-01/Q-02 的**决定性证据**，构成 P0-1 的全部动因。

| 项 | 值 |
|---|---|
| 终态 | `failed`，`error = {"code": "timeout", "detail": "全局超时"}` |
| 存活时长 | **1401 秒**（配置的 600 秒预算的 2.3 倍） |
| `result` | **NULL**（成果全丢） |
| `budget_used` | `{"iterations": 8, "tool_calls": 8, "input_tokens": 57788, "output_tokens": 27774}` |
| 暂停次数 | 5 次 `confirmation_request` |

**时间线关键段**（`[实测]`）：最后一段 `07:50:44.424 → 08:00:44.428` = **恰好 600.004 秒**触发 `timeout`。即超时不是从 run 创建起算，而是**从本次 `_invoke_and_finalize` 进入起算**——5 次暂停全部重置了计时器。

该段内还观测到：9 次工具调用；重复输出「外部采购 Agent 」；`message_delta` 6918 条中仅 4766 条不重复（**约 31% 是重复流式片段**）。

**代码对齐** `[代码]`：

- `runtime.py:446` — `timeout = (run.budget or {}).get("timeout_seconds") or 600`
- `runtime.py:~464` — `final_state = await asyncio.wait_for(self.graph.ainvoke(input_payload, config), timeout=timeout)`
- `_run` 与 `_resume_run` **各自**调用一次 `_invoke_and_finalize` → 各起一次计时
- `_pause_for_confirmation`（`runtime.py:505-518`）只落 `run.status` 与 `run.budget_used`，**不落任何时间信息**
- `runs/models.py:43-47` 只有 `started_at` / `finished_at`，**无 deadline / elapsed 字段**
- `_set_run_status`（`runtime.py:616-628`）**只在终态写 `finished_at`**，从不写 `started_at`

### 2.3 能力可见性的算术超约束（Q-03）

| 事实 | 证据 |
|---|---|
| `filesystem` 单个 MCP 展开 **14** 个工具 | `[实测]` `capability_tools` |
| Agent `tool_budget` = 8 / 6 | `[实测]` |
| 装配末尾硬切片 | `[代码]` `assembler.py` `return {"tools": tools[:tool_budget] + _meta_tools(), "skills": skills}` |
| pinned 是 **Agent 级**语义 | `[代码]` `retriever.py` `CapabilityBinding.mode == "pinned"` |
| Worker 的 capabilities 只经 `_task_scope` → `domain_ids` 参与重排 | `[代码]` `retriever.py` `order_by_scope` |

**结论** `[推断]`：`8 < 14` 意味着**只要 `filesystem` 在候选集中且排在前列，它单独就能吃掉全部名额**，Worker 领域能力被截断后模型看到的是一个"没有业务能力"的工具列表——**平台侧零提示、零事件、零日志**。这是"任务空转"的直接机制。

### 2.4 失败被降级为文本（Q-04）

`[代码]` `tools_builtin.py:171-190` `_procurement_request`：捕获 `httpx.HTTPError` 后**统一返回一句中文文本**（"采购 Agent 服务不可用（…）"），而不是抛错或返回结构化失败。模型收到的是 `ToolMessage` 里的自然语言，**无法区分"外部服务失败"与"业务结果为这个字符串"** → 模型据此继续推理并"完成"任务 = **假完成**。

同处的 5 个工具 `procurement_trigger/status/decisions/submit_decision/report`（`tools_builtin.py:192-234`）实现的是**阻塞式轮询**：模型必须依次调用 触发 → 查状态 → 查状态 → 取决策 → 取报告 才能完成一件事，正是原方案不变量 I1「单次派发」要避免的形态。

另注：`except httpx.HTTPError` **不覆盖** JSON 解析失败、schema 不匹配等异常，这些会直接冒泡成 run 级 `failed`。

### P0-1 运行时长账本与真全局超时

**目标**：E1（时长可测）+ E2（超时全局）+ E3（超时保留部分结果）。

**现状证据**

- `[实测]` `runs.started_at` 27/27 为 NULL；全库无任何时长列（§2.1）。
- `[实测]` run `47d69dcc` 存活 1401s，最后一段恰好 600.004s 被杀，`result = NULL`（§2.2）。
- `[代码]` `runtime.py:446` `timeout = (run.budget or {}).get("timeout_seconds") or 600`；`runtime.py:~464` `asyncio.wait_for(self.graph.ainvoke(...), timeout=timeout)` —— **每次调用各起一次计时**。
- `[代码]` `_pause_for_confirmation`（`runtime.py:505-518`）只落 `status` + `budget_used`，**不落任何时间**。
- `[代码]` `_set_run_status`（`runtime.py:616-628`）只在终态写 `finished_at`。
- `[代码]` `runs/models.py:43-47` 只有 `started_at` / `finished_at`，无 deadline/elapsed。

**变更点**

1. **写入 `started_at`**：在 `_run` 首次置 `running` 的同一次提交内写 `started_at`（唯一执行入口，天然覆盖 `manual`/`timer`/`alarm` 三种 trigger）。不在 `conversations/service.py` 创建 run 时写——因为 `pending` 可能长时间排队，会把排队时间算进执行时长（`[推断]` 当前无排队，但语义先分清）。
2. **引入绝对截止时间 `deadline_at`**：`deadline_at = started_at + timeout_seconds`，`timeout_seconds` 取 **run 创建时固化的 `run.budget` 快照**，缺省回退 Agent 配置，再缺省回退 `settings` 默认 600。**一次写入、永不重置**——这直接消灭 Q-02。
3. **暂停顺延**：`_pause_for_confirmation` 记录 `paused_at`；恢复时 `deadline_at += (now - paused_at)`。用"绝对时间 + 显式顺延"而非"累加剩余秒数"，避免多次分段后的漂移与舍入误差。
4. **执行段剩余时间**：`_invoke_and_finalize` 改为
   `remaining = (deadline_at - now).total_seconds()`；
   `remaining <= 0` → **不调用图**，直接走超时收尾；否则 `wait_for(..., timeout=remaining)`。
5. **活跃时长 `active_ms`**：每次进入执行段记录段起点，在暂停/终态处累加到 `runs.active_ms`。`elapsed_ms` 不落列，由 `finished_at - started_at` 计算（避免冗余与不一致）。
6. **超时保留部分结果**：新增 `_finalize_timeout(run_id, phase)`，写
   `result = {"schema":"run_result/v1","partial":true,"reason":"timeout","text":<最近一段 AI 文本或占位>,"steps_done":[...],"budget_used":{...}}`，
   `error = {"code":"timeout","detail":"...","elapsed_ms":...,"active_ms":...,"deadline_at":...}`。
   **不新增 run 状态**（保持 `failed` + 结构化 `error.code`），避免状态机外溢——`RUN_STATUSES`（`runs/models.py:15-23`）与 `TERMINAL_RUN_STATUSES`（`runtime.py:44`）保持不变。

**DDL**

```sql

ALTER TABLE runs ADD COLUMN active_ms    integer;
ALTER TABLE runs ADD COLUMN paused_at    timestamptz;
```

### P0-2 能力可见性硬保证 ✅ **已实施（M9-b 第 5 项）**

**目标**：E4——Worker 声明的必得能力 100% 进入模型工具列表；容量不足时**显式告警**，不静默切片。

**现状证据**

- `[代码]` `assembler.py` 装配末尾为 `return {"tools": tools[:tool_budget] + _meta_tools(), "skills": skills}` —— **硬切片**。
- `[代码]` pinned 是 **Agent 级**（`retriever.py` `CapabilityBinding.mode == "pinned"`）；Worker 的 capabilities 只经 `_task_scope` → `domain_ids` 参与 `order_by_scope` **重排**（`retriever.py`），**无保留名额**。
- `[实测]` `capability_bindings` 仅 1 条 pinned，且没有任何 Worker 的领域能力被 pinned。

**变更点**

1. **引入「必得集」概念**（装配语义的一等概念，不是新子系统）：
   - Agent 级 `pinned` 绑定；
   - 当前 run 的 `_task_scope` 命中项（Worker/任务声明的 `domain_ids`）在 **Worker run 内**视为必得。
2. **装配改为分区**：
   ```text
   tools = 必得集(全量保留) + 共享区[:max(0, tool_budget - len(必得集))] + meta_tools
   ```
   `meta_tools` 维持现状**不占** `tool_budget`（`[代码]` 现实现即如此），但要在本文与 `模块详细设计.md` 中明确写死，避免日后歧义。
3. **容量不足的处理顺序**（明确优先级，杜绝静默）：
   1. 若 `len(必得集) > tool_budget` → **不做切片**，全量保留必得集，并发射 `capability_overflow`；
   2. 若 `len(必得集) > MAX_TOOLS_HARD`（新增硬上限，建议 24，与上下文窗口联动）→ **本 run 显式失败**，`error.code = "tool_capacity_exceeded"`，提示缩小 `domain_ids` 或提高预算。**宁可报错，不可静默截断**。
4. **可见性自检接口**：给定 `agent_id`（+ 可选 `conversation_id` / `task_id`），返回装配全貌：
   `{candidates[], required[], kept[], dropped[], tool_budget, hard_limit, overflow: bool, reason}`。
   用于 CI、运维与"为什么我的工具没出现"的一键诊断。
5. **Worker 声明落地校验**：注册/发布 Worker 时（`docs/第三方Worker开发与注册规范.md` 流程内）校验 `len(引用能力展开后的工具数) ≤ tool_budget`。

6. `retriever.py` 的 `_task_scope` 返回值增加显式标记（`required_ids`），由 `assemble_tools` 消费；`order_by_scope` 的分层排序**保持现状**（回归保护）。

### P0-3 失败可信：结构化失败 + 禁止字符串降级 + 工具执行上下文

**目标**：E5——失败以结构化失败传播，模型可判别、平台可统计、用户可诊断；杜绝"假完成"。

**现状证据**

- `[代码]` `tools_builtin.py:171-190` `_procurement_request`：捕获 `httpx.HTTPError` 后**统一返回一句中文文本**（如"采购 Agent 服务不可用（…）"）。模型收到的是普通 `ToolMessage`，**无法区分"外部服务失败"与"业务结果就是这个字符串"** → 假完成根因。
- `[代码]` 同处 `except httpx.HTTPError` **不覆盖** JSON 解析失败 / schema 不匹配 / 业务非 2xx 语义错误；这些会冒泡成 run 级 `failed`。
- `[代码]` `graph.py` tools 节点 builtin 分支 `content, ok = await fn(dict(c["args"])), True` —— **`ok` 恒为 True**（元组右值就是字面量 `True`）。
- `[代码]` 同节点 mcp 分支 `ok = True` 亦为**硬编码**。
- `[代码]` `graph.py` verify 节点异常兜底为 `verdict = {"achieved": True, "feedback": ""}`（注释："验证失败视为达成，不阻断主链路"）——**验收失败反而记为达成**，第二个假完成入口。
- `[实测]` 全库 `run_events` 的 `error` 事件仅 **1** 条（§2.1）——失败面几乎不可观测。

**变更点**

1. **统一工具返回契约**（`ToolOutcome`）：
   ```json
   {"ok": true,  "content": <any>}
   {"ok": false, "error": {"code": "...", "detail": "...", "retryable": bool, "source": "builtin|mcp|external|engine"}}
   ```
   builtin / mcp 两条通道**都**按此判定 `ok`，删除两处 `ok = True` 硬编码。对既有 builtin 函数（返回裸字符串/字典）保留适配层，逐步迁移，**适配层不得吞异常**。
2. **禁止字符串降级**：`_procurement_request` 不再把异常翻译成中文文本；改为返回/抛出结构化失败。**代码评审红线：`except` 分支不得产出面向模型的自然语言结果。**
3. **失败分类码表**（固定枚举，禁止自由文本）：
   | code | 含义 | retryable |
   |---|---|---|
   | `external_unavailable` | 连接失败 / 超时 | true |
   | `external_rejected` | 对端返回业务拒绝（4xx/业务码） | false |
   | `invalid_args` | 本地入参校验失败 | false（模型改参后可为 true） |
   | `parse_error` | 响应不可解析（JSON/schema） | true |
   | `internal_error` | 平台内部异常 | 视情（默认 false） |
   | `denied_by_user` | 用户在确认点拒绝了高危调用（实施新增：不属"外部失败"，但不是成功） | false |

   实施落地于 `backend/app/modules/engine/tool_outcome.py`（码表 `TOOL_FAILURE_CODES` 为唯一真源，
   `RETRYABLE_BY_CODE` 给出默认值；未登记的 code 直接 `ValueError`，禁止自由文本码）。
   `source` 同为封闭枚举 `TOOL_SOURCES = (builtin, mcp, external, engine)`：`builtin` = 本进程工具自身、
   `mcp` = 外部 MCP 服务、`external` = 工具直连的第三方 HTTP（如 Open-Meteo / 采购 Agent）、
   `engine` = 平台引擎（如 verify 解析）。未登记 source 同样 `ValueError`。

4. **失败进上下文（I6）**：失败以 `ToolMessage`（结构化失败）注入，而非自然语言；同时 `tool_result` 事件携带 `ok=false` 与 `error`。
5. **连续失败熔断**：同一 run 内连续 `N`（可配，建议 3）次 `external_unavailable`/`parse_error` → 结束 run，`error.code = "tool_failure_loop"`，**不得进入终答**。这是"假完成"的第二道闸。
6. **修正 verify 兜底语义**：异常时 `achieved = False`（或显式 `unknown` 并按"未达成"处理），并在 `protected_context.verify_verdict` 里标注 `verify_error`。**不允许**验收失败被记为达成。
7. **结果信封 outcome 字段**（与 P0-5 联动）：`result.outcome ∈ {done, partial, failed, blocked}`。

**DDL**

无（复用 `runs.error` JSONB 与 `run_events.payload`）。
可选（P1，本项不实施）：`tool_invocations` 审计表（run_id / tool / args_hash / ok / error_code / duration_ms / idempotency_key）。

### P0-4 await 一等化：外部等待成为平台能力 ✅ **已实施（M9-b 第 6 项）**

**目标**：E8——分钟级外部流程用"单次派发 + 平台等待"表达，不再由模型阻塞轮询；等待可观测、可重启恢复、幂等重放。

**现状证据**

- `[代码]` `tools_builtin.py:192-234`：`procurement_trigger/status/decisions/submit_decision/report` 五个工具构成**阻塞式轮询**形态（违反 I1）。
- `[代码]` `runtime.py:_reconcile_orphans`（94-108）把 `running` **一律**标 `failed`；`TERMINAL_RUN_STATUSES`（`runtime.py:44`）、`tasks/router.py:44` `NON_TERMINAL_RUN_STATUSES`、`runs/router.py` `confirm_run` 的 409 守卫、`_resume_run` 的状态守卫——**新增等待状态必须同步这 5 处**，否则启动即被误杀或确认被静默忽略。
- `[实测]` `inbox_events` 中 `resume` / `capability_changed` **从未写入**（§2.5）。
- `[代码]` `_reconcile_awaiting_steps`（`runtime.py:585-614`）→ `reconcile_orphaned_awaits`（`tasks/service.py`）已能把挂起的 `awaiting_user` 支线收敛为 `blocked`——**这是可复用的既有机制**，原方案称"等待不是一等能力"过重（§1.3 第 1 条）。
- `[实测]` 7 个 `blocked` 支线的 note 后缀"（存量清洗）"**在代码中不存在**（代码模板为 `tasks/service.py:578` 的"run 已结束，待确认支线自动收敛"）→ 现网靠**人工 SQL 清洗**（Q-15）。

**变更点**

1. **新增 `await_broker` 表**：等待成为**平台持有的状态**，不再是模型上下文里的轮询循环。
2. **工具契约改为单次派发**：派发类工具返回
   `{"status":"accepted","await_id":...}`（**一次调用即返回**）；平台据此把 run 置 `waiting_external` 并结束本执行段（`graph.ainvoke` 正常返回或 interrupt）。
3. **触发工具面简化**：`status` / `report` 轮询工具从**模型可见工具列表**中移除（能力仍保留供平台 watcher 调用）。这一条是 I1 落地的关键——**模型看不到轮询工具，就不可能轮询**。
4. **回调入口（拉取式）**：`POST /open/awaits/{await_id}/resolve`，外部服务**主动调用平台**。
   - **一期不做平台主动回调**：主动出网会引入 SSRF 面（外部可控 URL + 平台凭据），与 `docs/设计方案.md` §1.4 边界不符。若未来确需推送，目标 URL 必须来自能力 payload 中声明的白名单且强制 scheme/host 校验。
5. **双重鉴权**：`X-API-Key`（复用 `open_api/router.py:27` `verify_api_key`，与 `settings.open_api_token` 比对）+ `callback_token`（`await_id` 的 HMAC 派生，防止越权解他人 await）。
6. **幂等（I5）**：`await_broker.idempotency_key` **唯一约束**；重复回调返回同一结果、不产生二次副作用。
7. **CAS 收敛**：`UPDATE await_broker SET status='granted', payload_out=... WHERE id=:id AND status='waiting'`，`rowcount=0` → 说明已被处理/已过期，返回既有状态而非重放。并用 `UniqueConstraint` 保证同一 `task_step` 不会有两个活跃 await。
8. **超时与过期**：`await_broker.deadline_at`（独立于 run 执行预算，来自业务 SLA，默认 `settings.await_default_timeout_seconds`）；到期 → `status='expired'` → run 从 `waiting_external` 恢复，注入**结构化失败**（P0-3 契约，不是自然语言）。
9. **预算语义（必须写清，否则误判）**：
   - 等待**不计入** `active_ms`；等待期间平台不占用执行资源；
   - 等待期间**保留** run 的 `deadline_at` 顺延权（与 P0-1 第 3 条同一机制）；
   - `iterations` / `tool_calls` **不因等待增长**（一次派发 = 一次工具调用）。
10. **统一暂停路径**：把 `_pause_for_confirmation` 与新的 `_pause_for_await` 收敛为一个 `_pause(run_id, kind, payload)`，`kind ∈ {confirm, await}`，避免两套暂停逻辑漂移。

| `await_broker.idempotency_key` 唯一 | 唯一约束落在 `(run_id, tool_name, idempotency_key)` | 单列唯一会让**不同 run** 的同参数调用互相顶掉（同一份报价单被两个会话派发是合法业务）；"同一 run 的同一逻辑等待只有一个活跃实例"才是真正要保证的不变量 |

| `await_resolved` 只承载 `granted` | `granted` 与 `cancelled` **共用** `await_resolved`（分列 `status`） | 二者都是"等待已落定的终局"，前端是同一渲染器按 `status` 着色；新增第 4 类事件会让 §7.1 注册表面积膨胀而无收益 |
| `await_started.payload.deadline_at` | 语义钉死为**等待超时点**；run 时长截止点另用 `run_deadline_at` | 二者是不同时钟（业务 SLA vs run 执行预算，后者还带暂停顺延）；同名会让前端与排障误读。`await_resolved`/`await_expired` 同规（`deadline_at` = 等待超时点，`run_deadline_at` = run 截止点） |
| 一期"平台主动回调外部服务" | **不做**，只做拉取式 `POST /open/awaits/{id}/resolve` | 主动出网 = 外部可控 URL + 平台凭据 = SSRF 面，与 `docs/设计方案.md` §1.4 边界不符 |
| 新增 `waiting_external` 专属任务条状态 | 任务条/看板**不新增**（`awaiting_confirm` 保持 `False`） | 否则每个等待都会把任务条从"执行中"翻成"待人工"，与语义不符（没人在等人工）。等待可见性由 run 状态 + `await_started` 事件 + 任务卡等待区块承担 |
| `expired` 与 `cancelled` 都"注入结构化失败" | 前者的 `error.code="await_expired"`，后者 `await_cancelled`；未知状态 `await_unresolved` | 三种失败的原因不同、运维动作也不同（查外部服务 / 查人工操作 / 查状态机bug），共用一个码会丢失可行动性 |

**已知边界（明确记录，不隐藏）**

**变更点**

1. **结果信封**（`schema` 版本化，向后兼容纯文本消费者）：
   ```json
   {
     "schema": "run_result/v1",
     "outcome": "done | partial | failed | blocked",
     "text": "终答文本（可能为空）",
     "cards": [{"card_type": "...", "payload": {...}}],
     "artifacts": [{"id": "uuid", "kind": "text|json|file|link", "name": "...", "mime": "...", "size": 1234}],
     "metrics": {"elapsed_ms": 0, "active_ms": 0, "iterations": 0, "tool_calls": 0, "input_tokens": 0, "output_tokens": 0},
     "reason": "timeout | rejected | tool_failure_loop | ... (可选)"
   }
   ```
   `metrics` 直接复用 `budget_used` + P0-1 的时长字段，**不新造账本**。
2. **新增 `run_artifacts` 表**：凡是"清单/报告/文件/大 JSON"，一律存表并以 `artifact_id` 引用；`result.text` 只放面向人的摘要。
3. **新增 `card` 事件**：结果卡与过程卡都走事件流，使卡片与事件序**对齐**，从而实现历史重放。
4. **历史重放**：前端新增 `card` 分支，从 `run_events` 重建卡片；`confirmation_request` 的内联卡片路径**保留**（兼容），但新卡片一律走 `card` 事件。
5. **压缩契约**（关键修正）：L1 折叠**不得作用于 artifact 引用**。折叠逻辑必须识别消息中的 artifact 引用并保留引用行（内容已在 DB，不在上下文）。同时把"结果必须先 artifact 化再进上下文"写成装配纪律。
6. **自动 artifact 化阈值**：单条工具观察 / 终答超 `settings.artifact_inline_max_chars`（建议 4000）→ 自动落 `run_artifacts`，上下文只留摘要 + 引用 id。
7. **失败也有结果**：与 P0-1 联动，超时/熔断 run 写 `outcome=partial|failed` 的信封 + `reason`，**不再 NULL**。

### P1-5 推送式进度

**目标**：进度由平台 watcher 推进并推送，不由模型轮询。

**现状证据**

- `[代码]` `graph.py:275` 任务卡已带 `"progress": {"done": progress_done, "total": progress_total}` —— **进度存在但只在任务卡内**，不是事件。
- `[实测]` `run_events` **无 `progress` 类型**（§2.1）。

**变更点**

1. 进度成为事件：新增 `progress` 事件（**同步注册表四处**），payload `{"done":int,"total":int,"label":str}`。
2. 平台侧 watcher（worker 循环内）按 `await_broker` 与 `task_steps` 变化推进进度并发事件；前端 `MessageStream` / `TaskBoard` 消费。
3. 与 P0-4 的等待联动：等待期间进度来自外部回调，而非模型。

**验收**

1. 前端在**无需模型参与**的情况下看到进度前进。
2. 进度事件可从历史重放。

**已实施 ✅（M9-c，commit 见 §12 实施记录）**

- **语义事件**：`EVENT_TYPES` 新增 `progress`（18→19），payload 固定为 `{"done":int,"total":int,"label":str}`，四处契约同步（后端 `EVENT_TYPES`、前端 `api/eventTypes.ts`、`tests/test_engine_frozen.py` 冻结清单、真实发射点）。发射点是**字符串字面量**（不经转发方法拼类型），故无需登记 `_DYNAMIC_EMIT_SITES`。
- **进度取数口径（反范式列，与任务卡同数）**：新增 `tasks/service.list_progress_snapshots(db)`，`SELECT runs.id/status + tasks.id/progress_done/progress_total`，`JOIN tasks ON tasks.conversation_id = runs.conversation_id`（`tasks.conversation_id` 唯一），行集由 **`runs.status IN NON_TERMINAL_RUN_STATUSES`** 驱动。进度直读 `tasks.progress_done/progress_total`（`recompute_progress` 是唯一写入口），因此**事件与任务卡/看板不会各说一套**。
- **附着实体的选择**：行集来自 **DB 非终态 run**，而非引擎内存里的 `_run_tasks`——等待外部回调（P0-4）/ 等待确认的 run 执行段已结束、不在 `_run_tasks` 中，但进度仍需推送。**不用** `runs.input->>'task_id'` 反查（避免 uuid cast 风险）。无会话归属的 run（如 timer）不匹配 → 不推。
- **`label` 口径与等待联动**：run 处于 `pending` / `waiting_external` / `paused_awaiting_confirm` 时给**阶段文案**（"排队中"/"等待外部回调"/"等待确认"），否则取**活跃步骤名**（`doing`/`awaiting_user`/`blocked`，`ORDER BY task_id, seq` 后取最小 seq）。run 进入/离开等待态时 label 变化 → 自然补发一份快照，等待期间的进度**由平台而非模型**表达（变更点 3）。
- **平台 watcher**：`runtime._progress_watcher()` + `_sweep_progress()`，周期 `settings.progress_watch_interval_seconds`（**默认 5.0s，即推送延迟上限**；空闲轮只发一次 `SELECT`）。**变化才发**：`_progress_seen[run_id]` 存上次 payload，先记账再比较；`total <= 0`（无步骤骨架的通用会话）不推首帧噪声但仍记账；每轮用存活集合裁剪记账，内存不随历史 run 增长；单轮异常只记日志、**不退出**。首次观测即算变化 → 进程重启后每个活跃 run 补发 1 条快照。
- **可重放（验收 2）**：事件经 `modules/runs/events.emit_event` 落 `run_events`（唯一写入口），因此既能按 `run_id` 经 SSE 实时广播，也能随历史查询重放；终态 `run_status` 到达后 SSE 流自然结束。
- **前端消费（验收 1）**：`MessageStream.tsx` 计划卡进度改取"**更新那一份**"（`progress` 事件 `seq` 大于计划卡 `seq` 才覆盖，避免终答轮的 5/5 被上一帧旧快照回退），并展示 `label`；`pages/Chat/index.tsx` 把 `progress` 纳入查询失效列表（任务看板/任务条随之刷新）；`RunTimeline.tsx` 增加事件渲染分支。
- **测试**：新增 `tests/test_progress_events.py` 17 例（事件登记与 payload 形状、非终态行集过滤、阶段文案优先于步骤名、最小 seq 取活跃步骤、首见/不变/推进/进出等待四类发射矩阵、无步骤骨架不推、终态裁剪记账、经唯一写入口落库、`start()` 真拉起 watcher、单轮异常不退出、`stop()` 可取消）。已对 4 处实现做变异验证（去掉"变化才发"、去掉记账裁剪、去掉阶段文案、`setdefault` 改 last-wins）——均被测试捕获。

- **竞态兜底**：并发两次提交穿过查重时由唯一索引只放行一个；落败方捕获 `IntegrityError` 后**整单 rollback**（本请求的 message 已 flush，只回滚 run 会留下"有消息无 run"），再重查胜出者返回（回滚后原实例已失效，不能复用）。
- **两个入口共用一个键**：`POST /conversations/{id}/messages` 与 `POST /tasks`；后者的判重**早于**建会话/任务骨架——否则"连点两次"会多出空会话 + 空主任务（键命中的 run 解析不出任务实例时返回 409，不给半截结果）。
- **前端**：`utils/id.ts` 的 `newClientMessageId()` 按**提交意图**取键（内容/附件变化即新意图重新取键，同内容重试复用同一键），`InputBar`（含 428 图片确认后的重发）与对话页提示卡「新开会话并发送」各自持键；`conversationsApi.sendMessage` 的可选参数改为对象，新增 `clientMessageId`。
- **测试**：新增 `tests/test_run_idempotency.py` 11 例（归一化 / schema 上限 / 查重口径与索引表达式同形 / 首提交快照 / 重复提交零副作用 / 竞态回滚返回胜者 / 无键时 `IntegrityError` 不吞 / `POST /tasks` 判重早于建骨架与 409 分支）。
- **诚实标注（本地禁连 DB）**：表达式部分唯一索引与 `IntegrityError` 竞态分支只经**假 DB + 编译期 DDL 比对**验证（ORM 索引定义与迁移 SQL 逐字一致），未在真实 PostgreSQL 上创建索引验证。

## §8 迁移与兼容

### 8.1 数据库迁移原则

1. **只加不改不删**：v1.6 全部 DDL 为 `ADD COLUMN`（可空）与 `CREATE TABLE`，无破坏性变更 → 可**先迁移后发版**，天然支持回滚（旧代码忽略新列）。
2. 新列在旧代码读路径上**必须有回退**：`deadline_at` 为 NULL 时按 `started_at + timeout_seconds` 兜底（`[推断]` 存量 27 行全为 NULL，必须覆盖）。
3. 新表**不写存量数据**：`await_broker` / `run_artifacts` 从零开始。

### 8.2 数据兼容矩阵

| 数据 | 兼容策略 | 依据 |
|---|---|---|
| 存量 `runs`（27 行）的 `result`（`{"text":...}`） | **读取时 coalesce** 为 `run_result/v0` 信封；不批量改写。✅ **已实施（P0-5）**：`timing.coalesce_result` 补 `cards`/`artifacts`/`metrics` 缺省 | §P0-5 迁移 |
| 存量 `runs` 的 `started_at = NULL` | 可选回填 `created_at`，**标注为估算**，不得用于 SLA 结论 | §P0-1 迁移 |
| 存量 `blocked` 支线（7 条，含人工后缀） | 不做数据清洗；`resolution.note` 的自由后缀在新代码中不再产生（P1-6） | §2.1 / Q-15 |
| 存量"中文降级文本"结果 | 不迁移（不可逆），仅在诊断文档中说明历史现象 | §P0-3 迁移 |

### 8.3 行为变更（需发布说明）

| 变更 | 用户可感知影响 |
|---|---|
| 超时按**全局**计算（不再分段重置） | 长流程更容易在总预算内被终止——但**保留部分结果**（净收益） |
| 必得能力不再被切片 | 部分 Agent 可见工具数上升（≤ 硬上限） |
| verify 异常不再记为"达成" | 失败率**上升**（更诚实）；假完成消失。**已实施（P0-3）** |
| 工具失败不再变成自然语言 | 模型行为改变：会更早求助/失败，而非"完成"。**已实施（P0-3）** |
| 连续 3 次瞬态工具失败即熔断 run | 长时间依赖单个不稳定外部服务的 run 会更早失败（带 `tool_failure_loop` + 涉及工具名）；阈值 `tool_failure_limit` 可配。**已实施（P0-3）** |
| `tool_result` 事件 payload 换字段 | 任何读取 `payload.name`/`payload.content` 的外部消费方需改读 `payload.tool`/`payload.result`（仓库内前端与 `skills_forge` 已同步）。**已实施（P0-3）** |
| 任意终态 run 的 `result` 不再为 NULL | 原来超时/取消后 `result` 可能是 `null`；现在**必有信封**（`outcome` 至少为 `partial`/`failed`），客户端旧逻辑若依赖 `result == null` 判断"无结果"需改读 `result.outcome`。**已实施（P0-5）** |
| 长结果不再整段内联，改为「产物引用 + 预览」 | 超 `artifact_inline_max_chars`(4000) 的工具观察与终答在上下文里只留引用行与 800 字符预览，完整内容进 `run_artifacts` 并经 `GET /artifacts/{id}` 取件；`result.text` 同样如此。**已实施（P0-5）** |
| 结果卡走 `card` 事件（与结果信封同源） | 历史任务重放时能看到结果卡；结果卡**只渲染元信息**（outcome / 耗时 / token / 产物），终答仍由 assistant 消息承担，不重复渲染。**已实施（P0-5）** |
| 装配不再对必得能力做切片 | 原 `tools[:tool_budget]` 会把 Agent `pinned` 与当前主任务域内能力一起切掉；现在必得集**全量保留**，共享区按剩余名额取。后果：部分 Agent 的**可见工具数上升**（硬上限 24 以内），这是设计意图，不是回归。**已实施（P0-2）** |
| 容量不足从"静默"变为"留痕" | 共享区被挤出时发 `capability_overflow`（含 `kept`/`dropped`），可在运行时间线看到黄色告警条目；运维/配置者据此判断是"加预算"还是"收敛能力"。**已实施（P0-2）** |
| 必得集超硬上限（24）时 run 直接失败 | 原来会静默切片并继续跑（模型拿残缺工具面空转）；现在 `error.code="tool_capacity_exceeded"`、`retryable=false`，结果信封照常产出。既有依赖"总能跑完"的监控需容忍此类失败。**已实施（P0-2）** |
| Worker 注册/发布新增容量硬门 | 引用能力展开后工具数 > 24 → 注册/发布 **422**（第三方注册与平台发布两条路径都拦）；`VersionBuildOut` 新增 `tool_count` 供配置者比对。存量 Worker 不受影响（只在下次发布时校验）。**已实施（P0-2）** |
| 派发类工具改为「一次派发 + 平台等待」 | `await_external_enabled=true` 时，模型调用 `procurement_trigger` 只出网一次即挂起，run 进入 `waiting_external`；工具观察在唤醒后才产生（`{"status":"resolved",...}` 或结构化失败）。**开关默认 `false`**，外部服务未实现回调契约前行为与旧版一致。**已实施（P0-4）** |
| 轮询类工具从模型可见列表移除 | `await_external_enabled=true` 时 `procurement_status` 不再进入装配结果（能力仍保留供平台/人工使用）。模型因此**不可能**轮询。**已实施（P0-4）** |
| 等待时长不计入 `active_ms` | run 暂停期间 `active_ms` 停表、`deadline_at` 顺延；`elapsed_ms` 仍含等待，故 `elapsed_ms` 可能远大于 `active_ms`（超出 `timeout_seconds` 也属正常）。看板/告警若用 `elapsed_ms` 判超时会误报。**已实施（P0-4）** |
| `resume` inbox 类型重新登记 | `engine/models.py:INBOX_EVENT_TYPES` 重新含 `resume`；未登记类型仍走 P0-6 的 `else` 兜底告警。**已实施（P0-4）** |
| 暂停态 run 的 `abort` 仍为空操作 | `interrupt()` 恢复点只能由恢复投递触发，故等待中 `abort` 不会立即终止 run（属既有暂停行为，未在本项扩大）。**已实施（P0-4）** |
| 新增等待状态 | 前端需展示等待态（旧前端会把它当作未知状态） |
| 模型工具列表移除轮询工具 | 依赖轮询的既有 prompt/技能需同步修订 |

### 8.4 回滚策略

| 层级 | 回滚方式 |
|---|---|
| 代码 | 回退到 `v1.5.0` tag；新列/新表被旧代码忽略 → **无需 DB 回滚** |
| 状态机 | 若 `waiting_external` 需撤销：把存量该状态 run 批量置 `failed` + `error.code="rolled_back"`（有明确出口） |
| 行为开关 | 超时全局化、必得集保留、verify 严格化分别用 settings 开关，便于灰度（**默认开启**） |
