---

## 1. 总体策略

1. **纵切优先**：每个里程碑以"可运行、可验证"为完成标准（DoD），不堆砌半成品模块
2. **后端先行，前端在 M3 后进场**：M3 结束时平台核心闭环（对话+引擎+能力）已可用（curl 验证），API 契约趋于稳定，前端再进场避免返工
3. **接口先冻结再开发**：M2 开工前冻结三处核心接口（LoopState / 钩子协议 / EngineBackend），这是模块详细设计 §5 的要求
4. **每个里程碑打 tag**：`v0.1-m1` … `v0.6-m6`，可回退、可复盘
5. **风险前置**：LangGraph 版本 API、MCP Server 兼容性两大外部风险在 M2/M3 最早期验证，不等开发到深处才踩

### M2 引擎（5 日）—— 平台心脏，风险最高段

**2a 接口冻结（0.5 日）**
- 冻结 `LoopState`、钩子协议（六钩子位签名）、`EngineBackend` 协议
- 确认 LangGraph 1.0.x 当前 API（interrupt / PostgresSaver / add_messages）写法，锁定版本号

**2b 最小闭环（2 日）**

| 任务 | 模块 |
|---|---|
| models 模块：Provider 抽象 + OpenAI 兼容实现 + 配置 API | models |
| engine 最小图：intent_router（先规则版）→ agent → END | engine |
| checkpointer：PostgresSaver 装配，thread=conversation | engine |
| inbox 事件队列 + LISTEN/NOTIFY + 轮询兜底 | engine |
| conversations：会话/消息落库、发消息 API | conversations |
| runs：创建/状态机 + run_events 写入 + SSE 端点（含 seq 续传） | runs |

**DoD（2b）**：curl 发消息 → SSE 实时看到 `message_delta` → 消息落库 → 重启进程后新消息接上历史上下文（检查点生效）。

**2c 完整机制（2.5 日）**

| 任务 | 模块 |
|---|---|
| planner / verify 节点 + 回环（限 3 次）+ plans 表 | engine |
| 确认点：interrupt 两处埋点 + confirmation API | engine + runs |
| hooks 链：audit → metering → budget → loop-detect | engine |
| 预算四闸（迭代/token/循环检测/超时） | engine |
| intent_router 小模型兜底 + 闲聊快速通道 | engine |
| model_usage_daily 记账（metering 回调） | models |

**DoD（2c）**：完整链路"发消息→计划→工具调用（先用 builtin 占位工具）→高危确认卡片→确认→完成"；人为造死循环被熔断且 run 标记 failed 带原因；kill 进程后 run 可恢复。

### M3 能力（4 日）—— 闭环成型，前端进场前最后一役

| 任务 | 模块 |
|---|---|
| capabilities 统一表 CRUD + payload 结构 + capability_bindings API | capabilities |
| 注册冒烟测试框架（test_info 执行器） | capabilities |

| 热注册：capability_changed 事件 → 重建池 | engine/capabilities |

| assembler：五区装配 + 预算分配 + L1/L2 两级压缩 + 保护名单 | discovery |

**DoD**：注册一个真实 MCP Server（filesystem 官方 Server 作首个验证对象）→ 冒烟测试通过 → Agent 语义命中并成功调用；关闭其某个工具后 Agent 上下文里该工具消失；连接池 kill 掉 Server 进程后 3 分钟内标记 unhealthy。

## 4. 验证策略

| 层 | 手段 |
|---|---|
| 单元测试 | pytest 覆盖纯逻辑：预算闸、压缩策略、路径计算、payload 校验（目标：核心逻辑 80%，其余豁免） |
| 集成冒烟 | 每里程碑一组 curl 脚本（scripts/smoke/），DoD 即脚本通过 |
| 真实回归 | M3 起保留一个"黄金任务集"（5 个真实任务），每次大改后全跑 |
| 前端 | 组件级不追覆盖，以 F 阶段 DoD 的操作流为准 |

## 5. 风险清单与前置验证

| 风险 | 影响 | 应对 | 验证时点 |
|---|---|---|---|
| LangGraph API 变动 | M2 返工 | 2a 即锁版本 + 写法验证，不裸奔到 2c | M2 开工首日 |
| MCP Server 质量参差 | M3 调试泥潭 | 首个验证对象选官方 filesystem Server；冒烟测试框架先行 | M3 首日 |
| 上下文装配调参（K 值/压缩阈值） | 体验差但非阻塞 | 参数全部配置化，收尾阶段用黄金任务集调 | 收尾 |
| 前端进度挤压后端 | 闭环延迟 | F5 可拆散后置；对话页（F2）优先保住核心体验 | 前端阶段 |
| 个人节奏中断 | 整体延期 | 每里程碑独立可用 + git tag，随时可停可续 | 全程 |

## 6. 里程碑检查点（每阶段结束问三个问题）

1. DoD 是否全部达成？（不可运行 = 未完成）
2. 有没有偏离四份设计文档的临时决定？有则补记 ADR
3. 下个阶段的接口是否受本阶段实现影响？影响则先改设计文档再动工
