| 项 | 内容 |

## 1. 项目定位

### 1.1 一句话定位

一个跑在个人 Mac 上的 Agent 平台：**以 Loop 引擎为核心调度中枢，通过注册进来的 MCP、工具、插件、Skill 完成明确的（非编程类）工作任务，知识库提供检索支撑，Web 界面使用**。

### 1.2 核心场景

- 日常工作任务处理（明确目标的任务，由 Agent 循环调用能力完成）
- 个人知识库构建与检索（RAG）
- 技术细节验证（平台本身也是试验场）
- 长期无人值守任务（定时触发 + 断点恢复）

### 1.3 设计原则（七条）

1. **循环要薄、上下文要管、经验要沉淀**——业界五个成熟系统（Claude Code / OpenClaw / dsh / Hermes / Kimi）的最大共识
2. **依赖边界 = 进程边界**——凡膨胀的、不确定的、第三方的依赖，一律推出核心进程，用协议（MCP/HTTP）通信
3. **一库多角色**——PostgreSQL 承担业务数据、向量库、能力索引、检查点、任务队列五种角色，不引入额外存储
4. **配置即代码**——compose 文件、初始化脚本、迁移全部入 git，任何时候一键重建
5. **概念收敛**——Tool / Skill / MCP / 插件统一为"能力"（Capability），一套注册中心、一套发现机制管到底
6. **确定性闸门**——LLM 的不确定性用确定性机制驯服：预算熔断、注册测试、人工确认、验证回环
7. **任务优先于会话**——先定任务架构（主任务=任务集合，子任务=可枚举步骤），再定会话架构（一次主任务实例 = 一个会话；支线子任务在同一会话内以步骤级 interrupt 处理，不新开会话、不新起子图）；能力（MCP/工具/插件/Skill）必须声明归属主任务，并保留「通用任务」兜底

### 1.4 与企业级方案（AgentForge）的差异声明

本平台不做：多用户/组织权限体系、双向安全网关、算力调度、工业协议对接（Fusion Gateway）、外部工作流引擎（Dify）。但吸收其：记忆整理 Job、入参确认卡片、注册即测试、上下文压缩保护名单、闹钟/定时任务分离等机制。

**关键架构判断：执行主体是 LLM 驱动的 Loop，确定性代码（MCP/插件）是 Loop 调用的工具。** 这与 AgentForge"workflow 为主体、LLM 做调度"相反，智能上限更高，因此对驯服不确定性的机制（预算/测试/确认/验证）依赖更重——这些机制在本方案中均为一等公民。

**第二条架构判断（M7a 补记）：主任务是"任务集合"，子任务是执行骨架。** 企业级场景里一次主任务（如"供应商报价对比"）必然跨多轮交互，且过程中随时冒出支线（单据缺字段、工艺无法识别、新供应商待录入）。因此：

- **先定任务架构，再定会话架构**：主任务模板（人工定义）→ 子任务骨架（主线必现 + 支线按需）→ 一个主任务实例固定一个会话
- **两支线**：模板预先定义的支线（optional 步骤）与运行期突发的支线（Agent 主动 `ask_user` / `declare_subtask` 抛出，步骤级 interrupt 暂停等答复）
- **能力有归属**：每个 MCP/plugin/tool 声明所属主任务，另有全局「通用任务集」承接公共能力（确认用户、查权限等）
- **进度是确定性事实**：由子任务状态算出，不由 LLM 估算；看板、任务卡（注入模型）、计划事件同源

## 3. 技术选型

| 层 | 选型 | 理由 | 落选者 |
|---|---|---|---|
| 编排框架 | **LangGraph**（1.0.x） | Agent Loop 工程化事实标准：状态图/循环/持久化/人工介入/流式开箱即用 | 自研循环（重复造轮）、dsh 式可换循环（过度工程） |
| 后端 | **Python 3.12+ / FastAPI / uv** | AI 生态第一语言；async 原生；uv 依赖管理快且锁死 | Node/Go（AI 生态弱） |
| ORM/迁移 | **SQLAlchemy 2.0 (async) + Alembic** | 成熟、异步、迁移可控 | — |
| 数据库 | **PostgreSQL 17 + pgvector** | 一库多角色；个人规模向量性能足够 | Milvus/Qdrant（运维成本）、Redis（一期能省） |
| 能力协议 | **MCP**（langchain-mcp-adapters） | 事实标准；自研插件复用同通道 | 私有插件协议 |
| 检查点 | **PostgresSaver** | LangGraph 官方组件，与主库同库 | SQLite（弱）、Redis（多余） |
| 容器运行时 | **OrbStack**（已装） | macOS 性能最优 | Docker Desktop（重）、Colima（无GUI不重要但生态弱） |
| 前端 | 后置（React/Vue 届时定） | 契约先行：OpenAPI + SSE | — |
| 调度 | **APScheduler** | 进程内定时，个人规模足够 | Celery（重） |

## 6. 核心机制设计

### 6.1 Loop 引擎：图结构与执行流

```
START
  → intent_router        闲聊→廉价模型直达；工作→继续
  → context_assembly     见 §6.2 发现与装配
  → planner → confirm_plan   生成计划（todo 入 plans 表，不塞上下文）；复杂任务计划提交前人审
  → agent ⇄ tools        ReAct 回环（LangGraph 条件边）
  → await_gate           派发类调用后进入外部等待闸门（P0-4）
  → verify               验证节点：达标→END；不达标→带反馈回 agent（计数）
  → 完成 → 结果信封 + run_artifacts（P0-5）→ END（或 预算熔断 / 转人工）
```

暂停点（interrupt）共四处，全部经 runtime 的 `_pause` 统一落库（结束执行段计时 + 记 `paused_at` + 落预算账本 + 置 run 状态）：任务计划提交前、高危工具调用前、支线澄清、外部等待。节点级细节见 [模块详细设计.md](./模块详细设计.md) §1.1.1。

- **inbox 队列化**（借鉴 dsh）：循环消费事件队列而非直接读消息数组；用户输入、定时触发、人工中断、恢复指令统一为队列事件 → 分叉/恢复/回放天然一致，且为二期拆 worker 预留接缝
- **检查点**：每超步自动落 PostgresSaver；进程崩溃/重启后从断点续跑
- **计划外置**（借鉴 Claude Code + Kimi）：长任务计划存 `plans` 表，Agent 每轮重读计划状态；前端渲染 todo 进度（plan_updated 事件）
- **预算熔断**（钩子实现）：max_iterations 硬上限 / 单任务 token 成本上限 / 同工具同参数连续 N 次循环检测 / **真全局超时**（M9-b/P0-1：`runs.deadline_at` 一次写入，按执行段累计 `active_ms`，暂停时长不计入并顺延截止点）
- **结构化错误**：工具异常返回结构化错误对象给模型，不抛堆栈；M9-b/P0-3 起统一为**失败码契约**（`TOOL_FAILURE_CODES` 9 码 + 可重试标记 + 连续失败熔断），模型与前端按码决策而非解析文案
- **结果一等公民**（M9-b/P0-5）：run 完成写结果信封（成功/失败 + 摘要 + 指标 + 产物清单）+ `run_artifacts` 落库，前端以结果卡呈现，历史重放同源
- **外部等待不计预算**（M9-b/P0-4）：等待时长不消耗 `active_ms` / 迭代 / 工具配额，等待态显式（`waiting_external`）

### 6.2 能力体系：统一模型、注册、发现、装配

**统一能力模型**：tool（函数）/ skill（Markdown 指令书+可选脚本，SKILL.md 惯例，yaml头 name/description）/ mcp（Server，含工具开关）/ plugin（自研 MCP Server）——四种 type 一张表。Skill 与 Tool 正交：Tool 是手，Skill 是操作手册。

**注册流程**：提交元数据 → 规范校验 → 按 `test_info` 跑冒烟测试（借鉴 AgentForge TEST.md）→ 通过才注册生效 → 自动 embedding 入能力索引。注册中心管理 MCP 连接生命周期（stdio/http，热注册/热摘除/健康检查）。

**发现机制三层**：

1. 静态绑定（pinned）：Agent 显式绑定常驻能力（高频 5–10 个）
2. **语义发现（主力）**：任务描述 → embedding → 能力索引 Top-K → 动态装配（控制上下文膨胀的核心手段）
3. Skill 渐进披露：初始只注入 ~100 token 元数据，Agent 按需 `load_skill(name)` 拉取全文

**归属分层（M7a，ADR-28）**：语义召回的 Top-K 还要按"能力属于哪个主任务"重排。每个 MCP/plugin/tool 在管理侧声明归属（`task_type_capabilities`），未被声明的兜底挂「通用任务」模板。运行期检索出候选后分层：**当前主任务域 → 通用任务集 → 其它域（全局）**，层内保持向量距离序；模板步骤 `capability_hint` 点名的能力在域内提权。装配时先放大候选（k×3）再分层截断，避免域内能力被全局高分挤掉——这是"软约束"：不禁止跨域调用，只是让本域能力优先占住 tool_budget。

**上下文装配器**（discovery/assembler）：

- token 预算分配：人格/画像（protected）｜技能元数据｜候选工具描述｜对话历史｜计划状态
- **保护名单**（借鉴 AgentForge）：人格文件、用户画像、活跃计划永不压缩
- 两级压缩（借鉴 Claude Code 五级压缩的简化）：① 裁剪折叠旧工具观察结果 → ② 全量摘要重启
- 触发条件：上下文使用率 ≥ 80%

**内置元工具**：`load_skill` / `search_more_tools`（检索即工具化）/ `search_knowledge`（知识库对引擎而言只是一个工具）/ `ask_user`（支线澄清，见 §6.8）/ `declare_subtask`（登记支线子任务，见 §6.8）。元工具不占 tool_budget，任何会话都可用。

### 6.3 技能沉淀闭环（skills_forge，借鉴 OpenClaw + Hermes）

```
任务成功或被纠正
  → 复盘节点："本次方法是否值得固化为 Skill？"
  → 生成 SKILL.md 草稿 → skill_proposals 表
  → 人工审核（Web 界面确认/驳回/编辑）
  → 入库（capabilities type=skill）→ 自动 embedding 进索引
  → 下次同类任务被语义发现命中
```

这是"越用越聪明"的实现路径（L4 爬山循环的第一步），也是平台随使用增值的核心抓手。任务失败/被纠正同样有沉淀价值（"别这么做"也写入）。

### 6.4 人工介入（借鉴 AgentForge 确认卡片）

- 确认点：任务单提交前（实体抽取结果打包确认，模型提取可能出错）；高危工具调用前（写操作/外部发送类）
- 确认点 3（M7a）：**支线子任务澄清**——Agent 调 `ask_user` 即暂停（同一 interrupt 通道，前端同一张卡片），用户以自由文本答复后主流程继续，答复固化进该支线步骤
- SSE `confirmation_request` 事件 → 前端渲染参数确认卡片（已解析参数自动填充）→ 用户确认/修改 → 恢复执行
- 配合检查点，暂停可跨小时/天

### 6.5 触发器体系（scheduler）

| 类型 | 行为 | 场景 |
|---|---|---|
| 手动 | 用户发消息 → run | 日常 |
| 定时任务 timer | cron 触发 → 生成任务单 → run | 周期性工作 |
| 闹钟 alarm | 到点纯提醒，不执行业务 | 提醒类 |
| 记忆整理 Job | 每日 03:00 | 记忆巩固 |

### 6.6 通知路由（借鉴 AgentForge）

run 完成时：若当前活跃会话与该任务相关 → 实时推送；否则进通知中心/次日摘要。

### 6.7 SSE 事件类型清单

全量 **16 类**（唯一真源 `engine/backend.py: EVENT_TYPES`，由 `tests/test_engine_frozen.py` 冻结；前端 `api/eventTypes.ts` 必须同集）：

`message_delta`（token 流）/ `message_reset` / `thought`（思考）/ `tool_call` / `tool_result` / `plan_updated` / `confirmation_request` / `budget_warning` / `run_status` / `error` / `context_compacted`（上下文压缩留痕）/ `card`（结果卡，P0-5）/ `capability_overflow`（装配溢出自检，P0-2）/ `await_started` / `await_resolved` / `await_expired`（外部等待三段，P0-4）

任务架构**不新增事件类型**（ADR-25）：主任务/子任务进度与支线变化复用 `plan_updated`（`items` 即子任务清单，加法带 `step_id`/`kind`，并带 `task_id` 与 `progress`），支线澄清复用 `confirmation_request`（`reason=subtask_clarification`）。旧前端忽略未知字段即可。

**受控扩展**（M9-b/P0-6）：新增事件类型必须同时改三处（后端 `EVENT_TYPES` + 前端 `eventTypes.ts` + 契约门测试），否则 CI 红；不需要新类型时只扩 payload。清单与分工见 [模块详细设计.md](./模块详细设计.md) §1.1.7。

### 6.8 任务架构：主任务 + 子任务（M7a）

**四层结构**（`tasks` 模块）：L1 定义层（主任务模板 + 子任务模板，人工维护，LLM 不自创）→ L2 实例层（主任务实例 + 子任务实例）→ L3 归属层（能力↔主任务）→ L4 会话层（一个主任务实例一个会话）。

```
主任务模板「供应商报价对比」
  ├─ 主线子任务：报价单解析 → 报价对比 → 生成对比报告
  └─ 支线子任务（optional）: 确认供应商名称 / 确认工艺处理方案 / 新增供应商

发起主任务 → 建会话 + 建任务实例（骨架由模板实例化）→ 每个子任务落到 task_steps
执行中 → 模型判定信息不足 → ask_user → 支线步骤置 awaiting_user → interrupt 暂停
用户答复 → POST /runs/{id}/confirm {answer} → 支线步骤 done（答复入 resolution）→ 主流程继续
全部主线子任务 done → 主任务 done（进度 100%）
```

| 机制 | 做法 | 理由 |
|---|---|---|
| 会话与主任务 1:1 | `tasks.conversation_id` UNIQUE；新开会话 = 新主任务实例 | 会话即任务档案，看板可直接按会话聚合；避免"一个会话里混多件事"导致上下文污染 |
| 支线子任务产生 | 模型调 `ask_user`（澄清型，阻塞）/ `declare_subtask`（登记型，不阻塞） | 支线种类无法穷举，必须在运行期由模型按现场情况发起 |
| 支线暂停与恢复 | 复用工具节点的 interrupt 通道 + `POST /runs/{id}/confirm` 文本答复 | 不引入子图/Swarm（复杂度前置且难以审计）；同一暂停语义只有一条代码路径 |
| 重放安全 | 支线步骤按 `(run_id, name)` 幂等复用，先登记再 interrupt | LangGraph 恢复会整节点重放，不幂等就会产生重复支线 |
| 计划来源 | planner 优先取主任务待办主线作为计划（`plans.items` 加法带 `step_id`），无主线时才 LLM 自由规划 | 用户预先定义的骨架比每次让 LLM 拆解更稳定，且与看板同源 |
| 进度计算 | `progress = count(status in (done, skipped)) / total`，由服务端确定性重算 | LLM 自报进度不可信；看板/任务卡/计划事件三处必须同一份事实 |
| 任务卡注入 | 当前主任务目标 + 进度 + 子任务清单（含已答复内容）拼进 protected 的系统提示词区，永不压缩 | 多轮长会话里模型会忘记"这是哪个主任务、还剩哪几项" |
| 新主任务软提示 | 同一会话中新话题判定成功时只回一个 suggestion（不落消息不建 run），用户选"新开会话"或"仍在本会话继续" | 硬拦会打断真实的长任务；软提示把架构决策权留给用户 |
| 越界记录 | 用户选"仍在本会话继续"时写 `tasks.out_of_scope`，任务卡追加"请专注当前主任务"提示 | 让模型知道本次越界，避免下一轮又输出别的任务的结论 |

## 7. 进程与部署模型

### 7.1 一期：单进程 + 四条硬纪律

```
[API 进程 uvicorn workers=1]              [独立容器/进程群]
  FastAPI + LangGraph engine                postgres:17+pgvector
  APScheduler + MCP 连接池                  解析服务（docling，REST）
  （纯 async I/O，依赖白名单）               MCP Server × N / 自研插件 × N
                                            （可选）Ollama
```

**纪律**：① 核心进程禁止同步阻塞操作（同步一律 `asyncio.to_thread` 或外推）；② workers=1（进程内单例状态：MCP 池/调度器）；③ 引擎调用走 `EngineBackend` 协议；④ runs 表从第一天就是队列/状态机语义。

**看门狗**：OrbStack `restart: always` + checkpointer 恢复 = 进程级自愈。

### 7.2 二期拆分触发条件（对号入座，不拍脑袋）

- 定时长任务成为常态（每日有 >10 分钟级自动 Loop）
- 核心代码频繁升级，重启打断任务变多
- 进程 RSS 持续增长、周均需手动重启
- 需要多 Loop 真正并行互不干扰

拆分方式：Engine Worker 独立进程，API↔Worker 用 PostgreSQL（runs 表 + LISTEN/NOTIFY）作队列，不引入 Redis。

### 7.3 依赖白名单（核心进程）

```
fastapi, uvicorn, langgraph, langchain-core,
langchain-openai(或其他provider包), langchain-mcp-adapters,
langchain-postgres, sqlalchemy[asyncio], asyncpg, alembic,
apscheduler, httpx, pydantic, pydantic-settings, pyjwt, passlib
```

**准入审查**：任何新依赖先问"能否推到独立进程"。解析（unstructured/docling）、本地推理（torch）等重依赖永远在容器隔离区。

### 7.4 docker-compose 服务清单

| 服务 | 镜像 | 说明 |
|---|---|---|
| postgres | pgvector/pgvector:pg17 | 数据卷 → ./data/postgres；restart: always |
| parser | docling 或 unstructured 服务镜像 | 按需启动，REST 接口 |
| api（可选容器化） | 自建 | 一期可直接 uv 跑宿主机，二期容器化 |
| 各 MCP Server | 社区镜像/自建 | 按注册表配置拉起 |
| searxng（可选 profile:search） | searxng/searxng:latest | 元搜索引擎，聚合多引擎；`127.0.0.1:8201`→8080；挂载自建 settings.yml（`formats:[html,json]`） |
| search-api（可选 profile:search） | 自建 services/websearch | 五级质量漏斗流水线 + MCP Server(`/mcp`) + REST(`/search` `/fetch` `/health` `/metrics`) + SQLite 缓存；`127.0.0.1:8204`→8200 |
| reranker（可选 profile:search） | 自建 torch CPU | `BAAI/bge-reranker-v2-m3` cross-encoder 精排；`127.0.0.1:8202`→8000；命名卷 `reranker_models` 缓存模型 |
| crawler（可选 profile:search） | unclecode/crawl4ai | JS 重页正文抽取升级路径（playwright/chromium）；`127.0.0.1:8203`→11235 |

> 自建网页搜索栈（4 服务统一挂 profile `search`，按需 `agentos search up` 拉起，默认 `docker compose up -d` 不受影响）：五级质量漏斗（查询理解→多路召回→加权 RRF 融合→cross-encoder 精排→正文抽取+片段级二次精排）+ MCP 接入，重依赖全部容器隔离（§7.3），`backend/` 零新依赖。详见 [docs/自建网页搜索服务.md](./自建网页搜索服务.md)（ADR-29）。

### 7.5 备份策略

- 每日 `pg_dump` → `./backup/`（保留 14 天，launchd 或容器 cron）
- 升级核心前强制备份；备份目录 gitignore

## 11. 演进路径与红线

### 11.1 明确不做（本期红线）

- 多用户/组织/权限体系
- 自修改软件（Agent 改平台自身代码）
- 多 Agent Swarm（>3 并行子 Agent）
- 消息平台网关（微信/TG 接入）——留作扩展点
- 内核级沙箱（容器隔离已覆盖个人威胁模型）

### 11.2 预留的演进方向

| 方向 | 接缝 |
|---|---|
| 拆 Engine Worker 进程 | EngineBackend 协议 + runs 队列语义 |
| 多 Agent 协作 | LangGraph 子图 + Supervisor 模式，agents 表已有多行能力 |
| 消息网关接入 | inbox 事件队列——网关只是新的生产者 |
| 换 LLM/Embedding 供应商 | Provider 接口 + 向量表带 model 标记（触发重建索引） |
| 多用户（若真需要） | auth 单点改造 + 全表加 user_id 的迁移成本 |
| 任务架构深化（嵌套子任务 / 多人协作） | `tasks.parent_task_id` 已是自引用列；子任务升级为真子图时，接缝在 `engine/graph.py` 的节点入口，前端只认 `tasks/board` 的聚合契约 |
| Worker 版本化与审批 | 定义层已在 m8 文件化为 `data/workers/<名>/<版本>/` 文件包（目录名即版本，天然可并存），加「版本指针 + 启用态」即可回放历史实例口径 |

## 12. 关键设计决策记录（ADR 摘要）

| # | 决策 | 理由 | 落选方案 |
|---|---|---|---|
| 1 | LangGraph 而非自研循环 | 循环/持久化/介入/流式全是刚需，自研无收益 | 手写 while 循环 |
| 2 | PostgreSQL 单库五角色 | 个人规模下运维成本最低，LangGraph 官方同款 checkpointer | PG+Redis+Milvus 组合 |
| 3 | 能力统一为一张表 | 概念收敛，注册/发现/开关一套机制 | MCP/Tools 分池（AgentForge式，企业需要，个人不需要） |
| 4 | 单进程起步 | 依赖已外推、检查点兜底；拆分条件明确 | 一开始就多进程（复杂度前置） |
| 5 | 计划外置 | 长任务不依赖上下文记性 | 计划塞上下文 |
| 6 | 技能沉淀带人工审核闸门 | 自动写技能有污染风险；人审成本极低 | 全自动沉淀 |
| 7 | 语义发现为主、静态绑定为辅 | 上下文膨胀是能力增长的第一死因 | 全量工具塞 prompt |
| 8 | 前端后置、契约先行 | 后端选型不受前端绑架，OpenAPI 冻结后并行开发 | 前后端同步开发 |
| 9 | 密码哈希直接用 bcrypt 库 | passlib 已停止维护且与 bcrypt>=4 存在兼容问题，功能上只需 hash/verify 两个函数（M1 实施时记） | passlib |
| 10 | 冻结接口的增量扩展（M2-2c 实施时记） | 2c 实现需要四处扩展：RunContext.limits 字段（预算四闸参数）、ToolResultInfo.args_snapshot 字段（循环指纹）、BudgetState.verify_retries 键（verify 回环计数）、EngineBackend.list_enabled_tools 方法（能力装配）；均为向后兼容的加法扩展，不影响 2a 冻结语义 | 重新开一个 v2 协议版本 |
| 11 | interrupt 重放纪律（M2-2c 实施时记） | 恢复时节点从头重放：① planner 生成计划与 confirm_plan 的 interrupt 拆成两个节点，重放不重复调 LLM；② tools 节点先 查全部调用风险、interrupt 一次、恢复后才逐个执行——副作用（工具执行/审计事件/循环计数）只发生在 interrupt 之后恰好一次 | 单节点内边生成边 interrupt |
| 12 | MCP 工具暴露名唯一化 mcp__{server}__{tool}（M3-e 实施时记） | 多 Server 工具名可能与 builtin 或其他 Server 重名；带 Server 前缀后全局唯一且可反解（tools 节点按前缀分派执行通道），schema 从连接池 tools_cache 取而非落库（避免两处同步） | 工具名直接用原名（重名冲突）/schema 存 capability_tools 表 |
| 13 | 悬空 tool_calls 发送前规范化（M3-f 实施时记） | run 在 tools 节点 interrupt 处被 abort 后，thread 里遗留无响应的 tool_calls，OpenAI 兼容端点会拒收整个会话；而 add_messages 归约只能 append 到末尾、无法插入中间位置。解法：agent 每轮发送前对消息做规范化（悬空补 [aborted] 空响应 + 响应吸附到对应 AIMessage 之后，幂等），补丁写回 checkpoint 位置不准无妨——下轮发送时重新吸附 | abort 时回写修复（abort 时机不可控，kill -9 场景失效）|
| 14 | 管道中间产物落盘而非落库（M4 实施时记） | 解析后的 markdown 存 data/parse/{doc_id}.md 而非 kb_docs.meta JSONB：体积大、无需查询、断点重试只需存在性判断；chunks 先入库（无向量）再补向量，两步各自幂等，重试按存量推断断点（产物→chunking，chunks→embedding） | 全部存 DB（JSONB 膨胀）/全重跑（浪费解析+切分） |
| 15 | docling-serve 新版 API /v1/convert/file（M4 实施时记） | 镜像 quay.io/docling-project/docling-serve-cpu 实际暴露 /v1/convert/*（v2 API）；旧文档的 /v1alpha/* 已 404，文件上传端点是 multipart /v1/convert/file（JSON 版 /v1/convert/source 不收文件）；中文 PDF 实测解析质量良好（cpu 镜像 arm64 3.6GB） | /v1alpha/*（已下线）/pypdf 等进程内解析（需自装依赖且布局还原能力弱）|
| 16 | timer 触发的 run 计划确认自动批准（M5 实施时记） | 无人值守的定时任务停在 confirm_plan interrupt 即死锁；trigger 随 config 传入图，confirm_plan 对 timer 直接放行；高危工具确认（确认点 2）仍保留 interrupt，暂停后用户回来处理。副作用：无会话 run 的 thread_id 是 run_id 兜底，persist_assistant_message 查不到 Conversation 行时跳过（run_events + runs.result 已留痕） | timer run 也人审（死锁）/全部确认点自动过（高危失控）|
| 17 | 记忆双产物落库而非全量重写（M5 实施时记） | 整理 Job LLM 一次输出 ===PLATFORM===/===DAILY=== 两段：daily 当日 upsert；platform 单文件按日段落（## {date}）追加，同日重跑替换该段；注入用全文拼 system_prompt（platform 全文 + 近 2 天 daily），向量仅为后续语义召回预留，注入路径不依赖向量 | 全量重写（丢历史）/向量检索式注入（漏关键事实）|
| 18 | skill 作为 capability 进语义检索池而非独立表（M6 实施时记） | 批准的草稿转 capabilities(type=skill) 复用 M3 的 index_capability 写向量与 enabled 开关；retriever 语义池加入 skill 类型后，assembler 命中时收集 SKILL.md 全文进 cache.skills（不展开为可调用工具——skill 是流程知识不是函数），context_assembly 拼 system_prompt「可用技能」区供 Agent 参照步骤。复盘钩子挂链尾 fire-and-forget，LLM 三问决定是否沉淀（已有能力覆盖则不沉淀） | skill 独立表 + 独立检索器（与能力体系分裂）/skill 展开为可调用工具（语义不符）|
| 19 | 分类缓存 + 单词输出 + 分类/装配并行（优化阶段实施时记） | 重复指令常见（「重试」「继续」），归一化文本+带图标记做 LRU 缓存命中则零延迟；非流式短调用延迟大头是输出 token，分类 prompt 改单词输出（chitchat/simple/complex 三选一）比 JSON 快数倍；语义装配（embedding+检索）与分类输入同为用户文本互不依赖，asyncio.gather 并行把装配延迟藏进分类等待，产物经 capability_cache 传给 context_assembly 复用 | simple 跳过语义装配的轻装配（实测 Agent 花 2 轮 search_more_tools 翻找工具，45.5s vs 并行 31.7s：单步知识库查询是高频场景，裁剪上下文诱发工具自救） |
| 20 | 计量归属到实际调用的 provider（优化阶段实施时记） | on_turn_end 增量扩展可选 provider_id（冻结协议加法扩展，同 ADR-10 先例）：意图分类/规划/验收等内部短调用与闲聊回复可能用轻量模型或对话内覆盖模型，token 应记真实 provider 账；意图分类调用此前完全漏记，一并补上 | 记 Agent 绑定主模型（轻量模型降本效果在账上不可见，账实不符） |
| 21 | 消息分页倒序取尾再反转 + before_id 游标（优化阶段实施时记） | 升序+limit 取到的是最旧一页，长会话最新消息反而看不到；必须倒序取尾部 limit 条再反转；游标取 anchor 的 created_at 严格小于，前端 prepend 后按滚动高度差恢复视口、按 id 去重（新消息使窗口前移会与 older 重叠） | offset 分页（有新消息时页漂移） |
| 22 | 切分引擎统一为 langchain-text-splitters 组合（切片管理实施时记） | MarkdownHeaderTextSplitter（标题分节，标题路径进 metadata，与原 heading_path 同构）+ RecursiveCharacterTextSplitter（节内递归切，separators 含中文句读，chunk_size/overlap 可调）：官方推荐组合恰是原手写实现的逻辑，统一后首切与重切（文档详情页 rechunk）同一条代码路径；strip_headers=False 保留标题在块内（检索命中自带章节上下文）；仅标题无正文的空节过滤保持旧行为；新增依赖仅纯 Python 轻量包 | 手写切分器扩展参数（双轨维护）/引入 langchain 主包检索期组件 EmbeddingsRedundantFilter/ContextualCompressionRetriever（偏重，列入债务清单备选） |
| 23 | 主任务=任务集合：模板人工定义 + 实例化骨架（M7a 实施时记） | 一次主任务（如供应商报价对比）必然跨多轮交互，且子任务清单在业务上是"可枚举的知识"而非模型每次的即兴拆解：故主任务/子任务做成两级实体——L1 模板（task_types + task_type_steps，人工维护，LLM 不自创）+ L2 实例（tasks + task_steps，发起时由模板实例化骨架，运行中允许追加支线）。前端左栏因此从"会话流水"变成"任务看板"（按模板分组、显示进度/待确认数），会话退化为任务的档案载体 | 会话即任务（一次对话一件事，多轮即失焦）/纯 LLM 即时拆解（不可复现、无法沉淀领域知识）/工作流引擎式编排（智能上限回到 AgentForge 水平） |
| 24 | 支线子任务用步骤级 interrupt，不引入子图/Swarm（M7a 实施时记） | 支线（单据缺供应商名、工艺无法识别、疑似新供应商）种类无法穷举，必须运行期由模型现场发起：新增两个常驻元工具——`ask_user`（澄清型，阻塞）与 `declare_subtask`（登记型，不阻塞）。澄清型实现为 tools 节点内的 interrupt：先登记/复用支线步骤（awaiting_user）→ 抛 `confirmation_request(reason=subtask_clarification)` → 用户自由文本答复经 `POST /runs/{id}/confirm` 回注 → 支线置 done 并固化答复 → 主流程继续。幂等靠 `(run_id, name)` 复用同一支线步骤（LangGraph 恢复会整节点重放） | 每支线起子图（图数量爆炸、状态难审计）/LangGraph Swarm 并行子 Agent（红线 11.1，企业场景需要的是"问人"不是"多 Agent 互聊"）/复用 confirm_plan（语义混淆，计划确认与业务澄清是两件事） |
| 25 | 任务进度复用 plan_updated 事件族，不新增事件类型（M7a 实施时记） | 前端需要"子任务清单 + 进度"的实时刷新，但事件族一旦扩张，所有消费者都要跟进：故复用 `plan_updated`——`items` 即子任务清单（加法扩展 `step_id`/`kind`），并带 `task_id` 与 `progress{done,total}`；支线澄清复用 `confirmation_request` 的既有卡片通道。冻结契约的加法扩展（同 ADR-10 先例），旧前端忽略新字段即可 | 新增 `task_updated`/`subtask_*` 事件（事件族扩张，SSE 契约与回放逻辑双双分裂） |
| 26 | 会话与主任务实例 1:1（M7a 实施时记） | `tasks.conversation_id` UNIQUE：一个会话承载一个主任务实例，看板可按会话聚合消息/运行/文件，任务卡注入也只需一个当前主任务；新发起主任务必落库实例，避免出现"有会话无任务"导致看板漏项。timer 触发的 run 无会话，任务实例的 conversation_id 允许 NULL | 一个会话挂多个主任务（上下文互相污染）/仅前端多会话无任务实体（进度与能力归属无处落库、后端无法注入任务卡） |
| 27 | 新主任务软提示 + 进度确定性计算（M7a 实施时记） | 两处"不交给 LLM 独自裁决"的判断：① 是否新主任务——发消息接口先做轻量判定，命中即只回 suggestion（不落消息、不建 run），由用户选"新开会话"或"仍在本会话继续"，后者写 `tasks.out_of_scope` 并在任务卡提示专注本主任务；② 进度百分比——由 `count(status in (done, skipped)) / total` 服务端重算（`PROGRESS_COUNTED_STATUSES`），看板/任务卡/计划事件三处同源，LLM 自报进度不参与状态机 | LLM 判定后自动新开任务（不可预期、丢上下文）/硬拦新话题（长任务中途的真实需求被拒）/进度由模型估算（数字不可信，与看板冲突时无法定位真伪） |
| 28 | 能力归属软约束：域内优先 + 通用任务集兜底（M7a 实施时记） | 企业平台里"这个工具是谁家的"必须可管理：能力↔主任务多对多（task_type_capabilities），未声明归属的能力启动 seed 兜底挂内建「通用任务」模板，解绑时同样落回该模板（保证每条能力永远至少一个归属，检索/看板/管理页三处不出现孤儿）。检索不做硬过滤而是**分层重排**：候选先放大 k×3，再按 本主任务域 → 通用任务集 → 其它域 重排后截断，模板步骤 `capability_hint` 在域内提权；装配结果 source 记录 task_domain/task_common/global 供溯源 | 硬过滤（跨域工具一次都调不到的可用性事故）/只存归属不影响检索（管理页好看但运行期无效果）/按归属拆多套检索器（与 M3 语义发现重复建设） |
| 29 | 自建网页搜索服务经 MCP 接入、五级质量漏斗（搜索服务实施时记） | 把搜索质量当可度量流水线：查询理解（≤4 路互补检索式）→ SearXNG 并发多路召回 → URL 归一化 + 加权 RRF 融合 → cross-encoder 精排（50→10）→ 正文抽取 + 片段级二次精排（每篇 2 段），每层有指标（recall@50 / route_agreement / nDCG@10 / span_hit）+ 消融对照 + 门禁回归；零按次成本。torch/chromium 重依赖全落 `services/` 容器隔离区（§7.3），backend 只经 MCP 消费零新依赖；RRF 只用排名不做量纲假设、对引擎构成漂移鲁棒；片段级精排把答案文本顶到模型眼前（span_hit=0.947）；输出预算服务端强制（默认 6000/硬顶 12000，护上下文 24000 阈）。顺带修 mcp_client 自愈两个真 bug：判死不摘除 `_conns` + `CancelledError`（BaseException）打死健康循环（改用 `_stopping` 标志判据） | 商业搜索 API（按次成本、数据出本机、引擎集不可控）/ builtin tool（重依赖进核心进程、绕开能力健康检查与语义发现）/ 加权分数求和融合（各引擎分数量纲不可比、归一化是无底洞、引擎一换即失准） |

### 13.2 债务清单（已知且接受，触发条件明确再还）

| # | 债务 | 影响 | 还债触发条件 |
|---|---|---|---|
| 1 | _INTENT_CACHE 是进程内缓存，重启丢失 | 重启后首批指令无缓存加速 | 可接受（重建成本低）；多实例部署时换 Redis |
| 2 | run_count 归属仍按 Agent 绑定主模型（on_run_end 未接 provider_id），与 token 归属口径不一致 | 对话内覆盖模型时 run 数记主模型账 | 出现第二个常驻 provider 且统计被用于决策时 |
| 3 | verify 节点自取 _get_llm + 轻量替换，未收敛到 _get_internal_llm | 代码重复，行为一致但两处维护 | 下次改 engine 时顺手收敛 |
| 4 | 知识库两级页的文档计数用全量 /kb/docs 前端 groupBy | 文档量大时首屏变慢 | 文档 >500 篇时加后端聚合接口 |
| 5 | MeteringHook._provider_cache 进程内 agent_id→provider_id 缓存无失效 | 改绑模型后旧账短时不准 | 可接受（记账统计分钟级、非计费）；多实例时一并处理 |
| 6 | 无集成级黄金任务自动化（当前为手工回归，见 13.3） | 回归靠人执行 | 出现第二次因回归漏测引入的 bug 时升级为 pytest 集成测试 |
| 7 | 检索期质量组件（langchain 主包 EmbeddingsRedundantFilter 向量去重 / ContextualCompressionRetriever 压缩）未引入 | 检索命中可能含冗余块 | 检索质量成为主要痛点时（ADR-22 落选记录） |
| 8 | 切片编辑/删除不产生审计记录 | 误删坏块不可追溯（可重新切分找回） | 出现误操作事故时 |
| 9 | 新主任务检测是轻量判定（启发式 + 轻量模型），存在漏判/误判 | 误判时用户需手动「新建任务」，漏判时用户看到软提示可直接忽略 | 误判率影响使用体感时，改为「近 N 轮 embedding 聚类 + 模板描述向量」判定 |
| 10 | 支线子任务的"答复→完成"没有语义校验（用户答非所问也置 done） | 极端情况下支线被假完成（本轮 e2e 实测：模型会重问，用户答复仍被记入） | 出现"答复无效但流程继续"的线上事故时，加一道轻量校验（答复是否回应了 question） |
| 11 | 任务模板无版本概念（改步骤只影响新实例，历史实例不回填） | 历史任务看板与最新模板口径不一致（但历史实例状态自洽） | 模板需要审计/回滚时加 task_type_versions |
| 12 | 能力归属只影响装配优先序，不限制调用 | 越界调用仍可能发生（软约束） | 出现"用了别的域的写操作工具"的事故时升级为硬过滤 + 归属审批 |

### 13.3 黄金任务集（手工回归基准，每次改动 engine/discovery 后跑）

| # | 输入 | 预期 |
|---|---|---|
| 1 | 「你好」 | 闲聊快速通道：无 plan/无工具，秒级回复 |
| 2 | 重复同一知识库查询两次 | 第二次明显更快（意图缓存命中），且直接调 search_knowledge 不翻元工具 |
| 3 | 「XX 文档里关于 YY 说了什么」 | simple 直通：无 plan、无确认，≤35s 内给出引用知识库的回答 |
| 4 | 「把知识库里的 XX 总结成要点并写入记忆」 | complex 链路：plan → 确认点 1 → 执行 → verify |
| 5 | 触发任一高危（write/dangerous）工具 | 确认点 2 interrupt，批准后执行、拒绝则跳过 |
| 6 | 带图消息（vision 模型） | 图片可见且仅保留最近 2 张历史图 |
| 7 | 任意任务跑完 | model_usage_daily 当日有记账；对话内换模型时 token 记到覆盖模型账 |
| 8 | 长会话（>200 条）打开 | 默认加载最新 200 条，「加载更早」向前翻页且视口不跳动 |
| 9 | 新建主任务「供应商报价对比」，发一条含报价单内容的消息 | 看板出现该任务卡片 + 进度条；planner 直接用模板主线作计划（不自由拆解）；任务卡（主任务/进度/子任务清单）进入系统提示词 |
| 10 | 报价单缺供应商名称，Agent 调 `ask_user` | 支线步骤登记为 awaiting_user（source=agent_raised）→ 卡片出现自由文本输入 → 答复后该步骤 done 且答复固化进 resolution → 主流程继续；重放不产生重复支线 |
| 11 | 同一会话里问一个明显无关的新话题 | 只回软提示卡（不落消息、不建 run）：「新开会话」则新任务实例 + 新会话；「仍在本会话继续」则落 `tasks.out_of_scope` 且任务卡出现专注提示 |
| 12 | 打开任务模板管理页，改步骤顺序/绑能力后新发任务 | 步骤 PUT 保序生效到新任务的子任务骨架；解绑能力后其归属落回「通用任务」，检索仍可命中（域内优先不再命中） |
