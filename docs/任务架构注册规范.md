# 任务架构注册规范

> 本规范把《企业级任务导向 Agent 平台架构方案》第三章沉淀为可自助操作的注册手册：
> **第三方照此注册 Worker（任务型 Agent），外部服务照此对齐集成契约。**
> 术语与字段以本仓库已落地代码为准（tasks / capabilities / engine / discovery / frontend）。
> 关联决策：M7a 任务架构见 ADR-23~28；本轮四条补充决策（plugin 前端 / 卡片 / Worker / 采购入驻）
> 分别对应下文 §5、§6、§2、§8。
> 第三方开发者入口：《第三方 Worker 开发与注册规范.md》（开放注册 API `/api/v1/open/*`，
> 静态令牌鉴权，支持 Worker + 能力捆绑一键注册）。

---

## 0. 一条总纲与三个不变量

**任务是第一等公民，会话是任务的执行外壳。** 先定义任务架构，再让会话架构服从它。

注册与运行必须遵守三个不可动摇的不变量：

1. **一会话一主任务**：主任务实例的 `conversation_id` 唯一；会话不是任务容器，是执行外壳。
2. **进度单一写入口**：进度只经 `tasks` 确定性重算（非 LLM 估算）；看板 / 任务卡 / 进度事件三处同源。
3. **通用任务集兜底**：未显式归属的能力自动落「通用任务」（`kind=common`，不可删 / 不可停用）。

## 1. 概念定义

| 概念 | 定义 | 落位（m8 文件化后） |
|---|---|---|
| 主任务（模板）= Worker | 一类可复用的工作目标，本质是一个任务型 Agent | 文件包 `data/workers/<名>/<版本>/WORKER.md` |
| 子任务（模板） | 主任务的分解步骤，分主线 / 支线 | `sub_workers/<名>/WORKER.md`（文件夹名 = 步骤引用） |
| 主任务（实例） | 一次具体执行，绑定唯一会话 | `tasks`（`worker_name` + `worker_version` 创建时锁定） |
| 子任务（实例） | 步骤的一次执行态（状态机） | `task_steps`（`worker_step_ref` 回指 sub_workers 文件夹名） |
| 能力 | 可执行单元，按功能四分类 | `capabilities`（`type=mcp\|tool\|plugin\|skill`，DB） |
| 能力归属 | 能力 ↔ 主任务多对多 | WORKER.md 头 `capabilities:` 工具引用清单（按能力名） |
| 通用任务 | 跨主任务共享能力的兑底域 | 内建常量 `COMMON_WORKER="__common__"`（不落库、无文件） |

> **m8 文件化**：Worker 定义层已完全去 DB（`task_types` / `task_type_steps` /
> `task_type_capabilities` 三表退役，迁移见 `g8d9e0f1a2b3`）；文件是唯一权威，
> 读取统一经 `app/modules/workers/registry.py`（mtime 指纹缓存，热路径零解析开销）。

**任务 = Worker（任务型 Agent），不是 Skill。** Worker 由一份 WORKER.md 式的三级逐层披露定义，
归 `tasks` 定义层；Skill（`capabilities.type=skill`，SKILL.md）归能力层，沉淀可复用方法论。
二者在**命名、存储、类别上完全切分**：Worker 定义任务、Skill 沉淀方法，Worker 可在 L3 引用 Skill，
但 Skill 永不被当作任务注册。平台 `skills_forge`（复盘沉淀 SKILL.md）保持不变。

| 维度 | Worker（任务定义） | Skill（能力） |
|---|---|---|
| 定义载体 | WORKER.md 三级披露（文件包 yaml 头 + 正文） | SKILL.md（`capabilities.type=skill`） |
| 归属层 | 定义层（tasks） | 能力层（capabilities） |
| 本质 | 任务型 Agent：干什么 / 怎么干 / 遇何问题 / 何时调哪个能力 | 一段可复用方法论片段 |
| 与执行 Agent | Worker 绑定执行 Agent（人格 / 模型 / 预算）承载运行 | 被 Worker 在 L3 引用，不反向定义任务 |

## 2. WORKER.md 三级逐层披露规范

每个 Worker（主任务 / 子任务）由三级披露定义，机制同 Skill 的 progressive disclosure，
但文件与命名切分。字段落在 WORKER.md 的 yaml 头：

| 级别 | 字段（主 / 子 WORKER.md 头） | 载入时机 | 要求 |
|---|---|---|---|
| **L1 元信息** | `name`（唯一、可检索）+ `description`（一句话讲清「什么场景用它」） | 常驻上下文 | 供看板展示与新主任务语义检测命中 |
| **L2 正文 playbook** | markdown 正文 | Worker 激活时注入永不压缩区 | 讲清五件事（见下） |
| **L3 引用资源** | `references`（yaml 数组）+ `references/*.md` 文件 | 执行到相应节点按需拉取 | 外部契约 / plugin 清单 / 数据契约 / 被引用的 Skill |

**L2 playbook 必须讲清五件事**（§3.2），外加必做的**第零步依赖预检**：

0. **依赖预检（必填段，置于「怎么干」之前）**：干这件事依赖哪些服务 / API / 数据源，
   如何探测（优先用内置工具 `probe_url`，read 级，探测可达性/状态码/延迟），
   不通时如何告知用户（明确说「依赖未就绪」并停止，不臆造数据、不空转主线）。
1. **干什么**：目标与产出。
2. **怎么干**：步骤顺序、输入输出、依赖能力。
3. **会遇到什么问题**：枚举执行中的异常 / 决策点。
4. **遇到问题如何处理**：每类问题对应的支线动作（`ask_user` 澄清 / `request_decision` 富交互 /
   `declare_subtask` 登记 / 自动兜底）。
5. **何时调哪个能力**：能力路由表（mcp / tool / plugin / 元工具）。

逐层披露的收益：上下文只在「需要时」展开——L1 让平台知道「有哪些任务、何时用」，
L2 让 Agent 知道「这个任务怎么干」，L3 让细节「用到才取」，既省 token 又保证指引权威可维护。

`references` 条目建议结构（数组，每项一个引用）：

```json
[
  {"kind": "rest_contract", "title": "外部集成契约", "path": "docs/任务架构注册规范.md", "section": "采购 Agent 改造契约"},
  {"kind": "plugin", "title": "决策面板", "capability": "采购决策面板"},
  {"kind": "skill", "title": "比价方法论", "capability": "some_skill"}
]
```

## 3. 注册一个 Worker（主任务）

**注册方式 = 放置文件包**（m8 起）：在 `data/workers/<名>/` 目录下放置文件包即完成注册，
运行时（意图识别 / 任务卡 / 能力域）直读文件，不再落 DB 定义层。

```text
data/workers/<Worker名>/              # 目录名 = 唯一标识（允许中文，= yaml 头 name）
  manifest.yaml                       # {enabled: bool, active_version: "v2"|null(=最新)}
  v1/WORKER.md                        # 主任务：yaml 头（name/description/icon/color/
                                       #   capabilities 工具引用清单/references）+ 正文 playbook
  v1/sub_workers/<子任务名>/WORKER.md # 子任务：yaml 头（seq/kind/optional/description/
                                       #   capability_hint）+ playbook 正文
  v1/sub_workers/<名>/references/*.md # 子任务引用文件
  v1/references/*.md                  # 主任务引用文件（LLM 按需加载）
  v1/tests/                           # 自动测试数据（按需）
  v2/…                                # 每个版本一个文件夹，手动构建递增
```

三步注册：

1. **建文件包**：在「能力 → Worker」页新建（生成 v1 脚手架），或直接放置上述目录结构；
   主 WORKER.md 填 L1 `description` + L2 正文（五件事 + 第零步依赖预检）+ L3 `references`。
   manifest.yaml 控制启停（`enabled`）与生效版本（`active_version`，缺省跟随最新）。
2. **拆子任务**：每个子任务一个文件夹（`sub_workers/<名>/WORKER.md`）——主线定 `seq` 排序
   （planner 按骨架推进），支线 `kind=branch` + `optional=true`（按需触发）；
   文件夹名 = 任务实例 `task_steps.worker_step_ref` 的回指键。
3. **填工具引用清单**：把该 Worker 要用的能力名写进主 WORKER.md 头 `capabilities:` 数组
   （文件管理器底部实时校验命中/缺失）；未被任何启用 Worker 引用的能力自动落「通用任务」兑底域。

**版本纪律**：只有生效版本可编辑，历史版本只读；编辑文件**不产生新版本**；
演进必须手动「构建新版本」（复制生效版本目录 → vN+1，active 指向新版本）。
任务创建时锁定当时的生效版本，全程读该版本文件；绑定版本目录被删时降级最新版本只显名称骨架。

**API 落点**（`workers/router.py`，前端「能力 → Worker」管理页）：

- `GET/POST /workers`（列表 / 新建脚手架）、`GET/PATCH/DELETE /workers/{name}`（详情 / 启停切版本 / 删除）
- `POST /workers/{name}/versions`（构建新版本）、`DELETE /workers/{name}/versions/{v}`（删历史版本）
- `GET /workers/{name}/tree?version=`（文件树）、`GET/PUT/POST/DELETE /workers/{name}/file?path=`（读写文件）
- `POST /workers/{name}/sub-workers`（子任务脚手架）、`GET /workers/{name}/capabilities`（引用清单校验）

### 3.1 子任务拆分决策树（主线 vs 支线）

```
这一步每次执行都必然发生、且有固定先后顺序？
├─ 是 → 主线(kind=main)：定 seq，planner 按骨架推进
└─ 否（仅在特定条件下需要，且需用户确认/决策）
        → 支线(kind=branch)：optional=true
          触发：Agent 调 ask_user(阻塞澄清) / request_decision(富交互决策) / declare_subtask(非阻塞登记)
          典型：缺关键信息 / 无法识别 / 需新增主数据 / 数据异常
```

### 3.2 capability_hint 用法

给步骤打检索提示（子任务 yaml 头 `capability_hint:` 能力名数组），装配时在本主任务域内提权——
不越权拉全局能力，只在「该主任务该步」优先。软约束而非白名单。

## 4. 能力四分类规范

按**功能**给能力定型，`capabilities.type` 承载语义；`category`（external/internal/builtin）
与 `risk_level`（read/write/dangerous）作为正交属性登记。

| 功能类 | 定义 | 归 `type` | 关键约束 |
|---|---|---|---|
| 读取类 | 从第三方平台读数据 | **mcp** | `risk_level=read`；payload 须含 transport |
| 写入类 | 向第三方平台写数据 | **mcp** | `risk_level=write\|dangerous`，过确认门 |
| 数据处理（简单） | 确定性轻量处理 | **tool** | 进程内 builtin，payload 携带注册键 + function schema |
| 数据处理（复杂） | 重逻辑 / 长管道处理 | **plugin** | 独立进程，异步桥接（触发即返回 + 状态查询） |
| 展示类 | 通过前端页面展示 / 交互 | **plugin** | **平台中只有 plugin 有前端页面**；由侧边栏渲染 |
| 方法论 | 可复用方法片段（非任务本身） | **skill** | SKILL.md；与 Worker 完全切分，可被 Worker 在 L3 引用 |

**payload 校验**（`capabilities/service.validate_payload`）：

- `plugin`：`payload.frontend`（前端清单）与 `payload.transport`（后端通道）**至少其一**；
  有 transport 则校验 transport；纯前端 plugin 可只有 frontend。
- `mcp`：须含合法 `transport`。
- `tool`（builtin）：payload 携带 `builtin`（注册键）+ `schema`（function-calling 签名）。

**外部长任务一律异步桥接**：触发后立即返回 + 独立状态查询 + 产出走知识库，规避单次执行超时上限。

## 5. plugin 前端渲染统一规范

平台中**只有 plugin 携带前端页面**；侧边栏（右侧可变宽栏，最大 ≤ 50vw、可拖拽）是 plugin 前端的
唯一宿主。plugin 在 `payload.frontend` 声明清单，统一两种渲染模式：

| 模式 | 适用 | `frontend` 清单 | 隔离 / 成本 |
|---|---|---|---|
| **iframe**（推荐外部 plugin） | plugin 自带完整 Web 页 | `{mode:"iframe", url, sandbox?, allowlist_origin?}` | 强隔离、跨技术栈；经 postMessage 桥接 |
| **server_driven**（推荐平台原生） | 轻交互（选 / 删 / 改一张表） | `{mode:"server_driven", schema}`（JSON UI schema） | 平台用 AntD 原生渲染、零自定义 JS、最轻 |

### 5.1 postMessage 桥接协议（iframe 模式标准握手）

- **iframe → 平台**：`READY`（就绪）/ `RESIZE`（`{width}` 宽提示）/ `SUBMIT`（`{data, applied?}` 结构化结果）/
  `CANCEL` / `CALL_MCP`（可选：请平台代调某写入类 mcp）。
- **平台 → iframe**：`WORKER_CONTEXT`（初始化：`{task_id, step_id, idempotency_key, data, theme, lang}`）。
- **握手**：iframe 发 `READY` → 平台回 `WORKER_CONTEXT`。
- **安全**：平台只接受 `allowlist_origin`（缺省取 `url` 的 origin）内的消息；iframe `sandbox` 最小授权。

`CALL_MCP` 代理路径当前未启用：平台回 `CALL_MCP_RESULT{ok:false}`，提示 plugin 在页面内直接调
写入类接口，并把结果并入 `SUBMIT.applied` 回传。

### 5.2 server_driven JSON UI schema（白名单组件）

```json
{
  "title": "确认供应商建档",
  "description": "识别到 3 个未管理供应商",
  "table": {
    "columns": [{"key": "name", "title": "供应商", "editable": true, "width": 160}],
    "rows": [{"name": "甲方"}],
    "selectable": true,
    "deletable": true
  },
  "fields": [{"name": "remark", "label": "备注", "type": "textarea"}],
  "actions": [{"key": "submit", "label": "确认", "kind": "submit", "style": "primary"}]
}
```

平台只用 AntD 渲染白名单组件（Table / Input / InputNumber / Button），**不执行 plugin JS**。

### 5.3 统一结构化回传契约（两模式一致）

```
{action: "submit" | "cancel", data: <array | object>, applied?: [{capability, result}]}
```

回传链路：侧边栏 `PluginHost` → `runsApi.confirm(runId, action, {data, applied})` →
`POST /runs/{id}/confirm`（`ConfirmIn{answer, data?, applied?}`）→ inbox `confirmation` →
`runtime` 构造 resume_value（`data/applied` 存在时为 `{answer, data, applied}` dict）→
`Command(resume=...)` → graph `request_decision` 消费 → `resolve_subtask` 写入子任务
`resolution`（JSONB）→ 引擎续跑。「直接调 mcp 落库」与「打包回传」两条路径统一到此契约
（落库结果并入 `applied`，同时回传）。

## 6. 聊天卡片统一规范

Agent 在聊天流「抛卡」是人在环的起点。复用现有 `confirmation_request` SSE 事件，泛化为 card 契约。
事件 shape 保持 `{reason, payload}` 不变，`reason` 即 `card_type`，前端按注册表分派渲染器。

### 6.1 卡片统一结构（`payload`，即 inner）

```json
{
  "card_type": "interactive_decision",
  "title": "确认供应商建档",
  "summary": "识别到 3 个未管理供应商",
  "severity": "info | warn | danger",
  "body": {},
  "actions": [
    {"key": "open", "label": "去处理", "kind": "open_sidebar", "style": "primary"},
    {"key": "skip", "label": "跳过", "kind": "reject"}
  ],
  "sidebar": {"plugin_capability_id": "...", "frontend": {}, "init_data": {}, "width_hint": 0.5, "step_id": "...", "idempotency_key": "..."},
  "step_id": "...",
  "idempotency_key": "..."
}
```

- `card_type` 决定用哪个渲染器；`body` 主体可为字段 / 列表 / 表格 / diff。
- `actions.kind`：`confirm` / `reject` / `open_sidebar` / `custom`。
- `sidebar` 仅 `open_sidebar` 卡需要，指向 plugin 前端（§5）；前端构造 `SidebarDescriptor`
  时补 `run_id`（来自当前确认 run）。

### 6.2 内置卡片（平台提供，注册表 `CARD_REGISTRY`）

| card_type | 用途 | 触发 |
|---|---|---|
| `plan_review` | 计划确认 | planner 生成计划后（仅 complex） |
| `high_risk_tool` | 高危工具确认 | tools 节点风险预查命中 write/dangerous |
| `subtask_clarification` | 支线澄清（文本答复） | Agent 调 `ask_user` |
| `interactive_decision` | **交互决策卡（带 sidebar）** | Agent 调 `request_decision` |

> `task_switch_suggested`（新主任务软提示）走独立 `TaskSwitchCard`（`send_message` 返回值，非 SSE 确认事件）。

### 6.3 自定义卡片（业务扩展，不改平台内核）

卡片渲染器由 `CardRenderer` 按 `card_type` 分派。业务方两条自定义路径：

- **(a) 声明式模板**：未命中注册表的 `card_type` 自动落 `GenericCard`——按
  `{title, summary, severity, body, actions}` 通用渲染（server_driven 思路），无需改内核。
- **(b) plugin 自带卡面**：`actions.kind=open_sidebar` → 按 §5 加载 plugin 前端（iframe），
  plugin 既渲染侧边栏、也可承载富交互卡面。

### 6.4 元工具 request_decision（抛交互决策卡）

`request_decision` 是常驻元工具（不占 tool_budget），参数：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `title` | string | ✓ | 决策卡标题 |
| `summary` | string | | 一句话说明为何需用户处理 |
| `severity` | enum(info,warn,danger) | | 强调级别，默认 info |
| `body` | object | | 卡片主体（字段 / 列表 / 表格），供卡面预览 |
| `plugin` | string | | 承载侧边栏前端的 plugin 能力名（须 `type=plugin` 且声明 frontend）；留空则只展示 body |
| `init_data` | object | | 传给 plugin 前端的初始化数据（经 WORKER_CONTEXT 下发） |

执行纪律（同 `ask_user`）：登记支线 → `interrupt` 抛卡（`reason=interactive_decision`）→
本轮其余工具调用不执行 → 用户结构化回传 → `resolve_subtask` 回填 `resolution`
（`action=submit` 置 done / `cancel` 置 skipped）→ 续跑。重放幂等。

## 7. 运行规范（定义完毕后必须遵守）

0. **依赖预检规范**：任务执行前先检查依赖项（服务是否启动、API 是否可达，用 `probe_url`）；
   预检不通过则**直接告知用户依赖未就绪并停止**，不进入任务、不臆造数据。只有依赖全部通过
   才正式开始主线。外部依赖降级提示（如服务不可用）不算失败，如实呈现即可。
1. **会话规范**：一主任务实例一会话；子任务在同一会话内推进；检测到疑似新主任务
   （Worker L1 语义比对，阈值 `TASK_SWITCH_THRESHOLD=0.75`），**软提示**新开会话（不阻断），
   用户坚持则本会话继续并记越界（`tasks.out_of_scope`）。
2. **进度规范**：进度只经唯一写入口确定性重算；看板 / 任务卡 / 事件三处同源；前端不本地估算。
3. **支线人在环规范**：支线以步骤级挂起 + 幂等键防重放；需人工介入时**抛卡 → 侧边栏 plugin 前端
   处理 → 结构化回传**；回填 `resolution` 并固化；主线收口且无未决支线时自动跳过未触发支线并置任务完成。
4. **归属规范**：能力归属由 WORKER.md 头 `capabilities:` 清单声明；未被任何启用 Worker
   引用的能力自动落「通用任务」兑底域；检索按「本域 → 通用 → 全局」分层。
5. **描述规范**：每个 Worker 必须具备 WORKER.md（L1 简要 + L2 playbook）；L2 随任务卡注入永不压缩区。
6. **模板规范**：Worker 文件包人工维护、LLM 不自创；新版本必须手动构建（编辑不产生新版本）；
   主任务有实例时删 Worker 不影响实例（降级显示名称）。
7. **切分规范**：Worker（WORKER.md，任务）与 Skill（SKILL.md，能力）命名、存储、类别彻底分离；
   Worker 可在 L3 引用 Skill，Skill 不得被当作任务注册。

## 8. 采购 Agent 改造契约

采购报价对比 Agent 是**首个外部服务入驻案例**（决策4）：保持独立外部服务（FastAPI + SQLite +
异步 + SSE，自带九段流水线与四类决策 REST），**不并入平台、平台不落其业务代码**。平台保持
「薄编排层」，任务执行留在外部；平台只定标准，采购 Agent 按本契约改造对齐。

### 8.1 平台侧已登记（新增代码极少，见 `tasks/procurement_seed.py`）

- **一个 Worker 文件包**「供应商报价对比」（`data/workers/供应商报价对比/v1/`，WORKER.md：
  L1 简要 + L2 playbook 讲清九段流水线的干什么 / 怎么干 / 问题清单 / 能力路由 +
  sub_workers/ 5 主线 + 4 支线 + L3 引用本契约；启动幂等 seed，已存在不覆盖用户编辑）。
- **一组桥接能力**（builtin tool，照法规爬虫异步范式，见 `engine/tools_builtin.py`）：

  | 能力名 | risk | 映射 REST | 说明 |
  |---|---|---|---|
  | `procurement_trigger` | write | `POST /worker/trigger` | 异步触发解析，立即返回 task_id |
  | `procurement_status` | read | `GET /worker/status/{id}` | 轮询九段流水线进度 |
  | `procurement_decisions` | read | `GET /worker/decisions/{id}` | 拉待决策面（schema 与卡片 / 侧边栏对齐） |
  | `procurement_submit_decision` | write | `POST /worker/decisions/{decision_id}` | 回写侧边栏结构化结果并落库 |
  | `procurement_report` | read | `GET /worker/report/{id}` | 取对比报告 / AI 综合分析 |

- **一个 plugin**「采购决策面板」（`type=plugin`、`category=external`、`payload.frontend` 为 iframe
  清单，`url={base}/worker/ui`，`allowlist_origin` 取 base 同源）。
- **主线子任务 5 步**（映射九段流水线）：报价单接入与解析 → 语义映射与校验 → 机械对比 →
  AI 综合分析 → 生成对比报告。
- **支线子任务 4 类**（映射决策点，`kind=branch`+`optional=true`）：确认新增供应商、
  确认工艺处理方案、绑定项目、数据纠错——正是「侧边栏人在环」的典型场景。
- **配置**：`procurement_agent_base_url`（默认 `http://localhost:8100`，环境变量可覆盖）。

### 8.2 采购 Agent 需按平台规范改造（关键，允许改外部服务）

1. **暴露标准外部 Worker 集成契约 REST**：
   - `POST /worker/trigger`：异步触发解析 → 返回 `{task_id}`（不等完成）。
   - `GET /worker/status/{id}`：返回 `{status, stage, progress}`（九段流水线进度）。
   - `GET /worker/decisions/{id}`：返回待决策面数组，每项
     `{decision_id, type, title, summary, severity, body, init_data}`，**schema 与卡片 / 侧边栏对齐**
     （`body` 供卡面预览，`init_data` 供侧边栏 plugin 前端初始化）。
   - `POST /worker/decisions/{decision_id}`：接收 `{data}`（侧边栏结构化回传）并落库。
   - `GET /worker/report/{id}`：返回对比报告 / AI 分析（格式对齐知识库入库管道）。
2. **四类决策页改造为可被平台侧边栏加载的 plugin 前端**（`{base}/worker/ui`）：遵守 §5.1 postMessage
   桥接协议（iframe）——收 `WORKER_CONTEXT` 初始化、发 `READY`、用户处理完发 `SUBMIT{data, applied?}`
   或 `CANCEL`；或返回 JSON UI schema 走 server_driven。
3. **统一鉴权 / CORS / 端口**（沿用其 port-manager），`allowlist_origin` 与平台侧 iframe 校验一致。
4. **产出回流**：对比报告 / AI 分析经知识库管道入库并向量化，供 `search_knowledge` 跨任务检索复用。

### 8.3 人在环闭环（时序）

```
Agent 推进主线 → procurement_decisions 拉到待决策面
  → request_decision(title, plugin=采购决策面板, init_data=决策面) 抛 interactive_decision 卡
  → 用户点「去处理」→ 侧边栏 iframe 加载 {base}/worker/ui → WORKER_CONTEXT 下发 init_data
  → 用户选/删/改 → SUBMIT{data} → runsApi.confirm(runId, "submit", {data})
  → graph 恢复 → procurement_submit_decision(decision_id, data) 写回采购 Agent 落库
  → resolve_subtask 回填 resolution → 支线 done → 主线续跑
```

> 案例结论：平台**不为采购 Agent 改动内核、也不吞并其代码**——只用 Worker + 桥接能力 +
> 卡片 / 侧边栏规范把它接进来。这验证了：① 架构表达力（主任务 / 子任务 / 支线 / 归属 /
> 异步桥接 / 产出沉淀全有对应位置）；② 平台的「薄」（标准在此、执行在外部，采购按规范改造即可入驻）。

## 附录：注册检查清单

注册一个新 Worker，逐项自检：

- [ ] 文件包 `data/workers/<名>/`：主 WORKER.md 头 `name` 与目录名一致、L1 `description`、
      L2 正文（五件事齐全 + 第零步依赖预检）、L3 `references`；manifest.yaml 启停正确。

      每步 L1 `description` + L2 正文 + `capability_hint`；头 `name` 与文件夹一致。
- [ ] 能力按四分类登记（`type` + `category` + `risk_level` + `payload`，DB 能力层）；plugin 声明 `frontend` 清单。
- [ ] 主 WORKER.md 头 `capabilities:` 清单全部命中已注册能力（文件管理器底部校验无缺失）；
      未引用能力自动落通用任务。
