# 自建网页搜索服务（五级质量漏斗）

> 独立自托管服务 `services/websearch/`，把「网页搜索」当成一条**可度量的质量流水线**来搭建，
> 而不是「调一个搜索 API」。零按次查询成本，输出已排序、已去重、可直接喂给 LLM 的结构化结果。
> 平台侧只经 **MCP Streamable HTTP** 通道消费（能力名 `websearch`），`backend/` 零新依赖。

本文是这个服务的**权威说明**：架构、每层的度量口径、参数调优、评测基线、排障。
设计方案 §7.4 只留一行索引指向这里；运维手册只留启停与三条症状排查。

---

## 0. 一句话与三条工程判断

搜索质量不是「找个好引擎」，而是一条漏斗——每层解决上层解决不了的问题，且每层都有一个数字能证明它做了事：

```
查询理解 → 多路并发召回 → 归一化 + 加权 RRF 融合 → cross-encoder 精排 → 正文抽取 + 片段级二次精排
   (路)        (recall@50)      (route_agreement)        (nDCG@10/MRR)         (片段召回率 span_hit)
```

三条贯穿实现的判断：

1. **召回决定上限、重排决定体感**：候选窗口里没有的正确答案，再强的精排也捞不回来；但窗口里有了，排在第 30 位和排在第 1 位对 LLM 是天壤之别。所以融合层先把 `recall@50` 顶满，精排层再决定「哪 10 条、什么顺序」。
2. **多路召回 + 融合的收益 > 单路调参**：同一句话换 4 种检索式、跨多个引擎，各自排序后用 RRF 融合——比在单一引擎上反复调关键词稳健得多。基线里这一步把 `recall@50` 从 0.773 抬到 0.909（+0.136）、`MRR` 从 0.242 抬到 0.449（+0.207），是全流水线**最可信的一段结构性增益**（见 §8）。
3. **没有度量就没有质量**：每层都有指标、每次改动都能跑 `eval/run.py` 出一个数字答案、`compare.py` 对基线回归超阈值即 `exit 1`（可挂 CI）。引擎死活、精排有没有做事、缓存命中多少——全部变成数字而非玄学。

## 1. ADR-29：为什么这么设计

| 决策 | 选择 | 理由 | 落选方案 |
|---|---|---|---|
| **接入通道** | MCP Streamable HTTP（`type=mcp` 能力） | 直接复用平台既有的冒烟测试 / 60s 健康探活 / 语义发现 / 工具级开关 / 断连自愈；`backend/` 零新依赖，只多一层薄 seed | builtin tool（要把 httpx 调用、降级、缓存全塞进核心进程，且绕开能力体系的健康/发现机制） |
| **算力边界** | 全量本地 CPU，重依赖容器隔离 | 设计方案 §7.3 硬纪律：torch / playwright / chromium **永不进核心进程**。全部落在 `services/`，平台只经 MCP 消费 | 云端搜索 API（有按次成本、数据出本机、引擎集不可控） |
| **融合算法** | 加权 RRF（Reciprocal Rank Fusion，`k=60`） | 只用**排名**不用分数——不对各引擎的分数量纲做任何假设，免调归一化，对引擎构成漂移天然鲁棒。路权重 `w_r` 表达「这一路更可信」 | 加权分数求和（各引擎分数量纲不可比，归一化参数是无底洞，引擎一换就失准） |
| **片段级二次精排** | 文档级选「哪几篇」+ 片段级选「每篇哪 2 段」 | 光选对文档不够：一篇 8000 字的官方文档里，回答问题的可能就那 2 段。片段级精排把答案文本顶到模型眼前——`span_hit=0.947` 是直接证据（94.7% 的带标准答案串的查询，输出片段里命中了答案） | 只做文档级精排 + 抽首段（答案常在中段，首段命中率低） |
| **抽取分层** | `EXTRACTOR=auto`：trafilatura 快路优先，JS/403 才升级 Crawl4AI | 把 Chromium 只花在真正需要的页面上：进程内 trafilatura 亚秒级、无浏览器；正文 <400 字或被拦时才升级到 crawl4ai `/md`。延迟与内存都可控 | Crawl4AI 独占抽取（每页都起浏览器，10 篇 = 数十秒 + 数 GB 内存） |
| **LLM 检索式扩写** | `ROUTE_LLM=false` 默认关闭 | 保「零按次成本」与**结果可复现**（评测要求同一 query 多次跑结果稳定；LLM 扩写引入随机性会污染回归对照） | 默认开（每次查询多一次 LLM 调用 + 结果不可复现） |
| **缓存** | stdlib `sqlite3` 两层（query / url）+ 指标表 | 零依赖、可 `sqlite3` CLI 直接查、跨重启保留。整条流水线可被 query_cache 短路（基线实测冷 6032ms → 热 0ms，6032× 加速） | 进程内 LRU（重启即失，无法跨评测轮次复用） |

**遵循的既有约束**（这三条直接决定了服务的边界参数）：

- §7.3：重依赖只在容器隔离区 → 全部落 `services/`，平台侧只经 MCP 通道消费。
- 引擎不截断工具结果（`graph.py` 直接 `ToolMessage(content=str(content))`），而 `context_compact_threshold=24000` → **输出预算由服务端强制**（`max_chars` 默认 6000、硬上限 12000）。
- MCP 健康探活 60s/次、连续 3 次失败（180s）即摘除；冒烟单用例上限 30s（`smoke.py`）→ **服务端全链路硬超时 25s**（各阶段独立超时 + 总预算），且必须 < 30s。

## 2. 架构与拓扑

root `docker-compose.yml` 新增 4 个服务，统一挂 `profiles: ["search"]`——默认 `docker compose up -d`（db + parser）不受影响，重资源栈按需拉起（`agentos search up` 或 `make search-up`）。

| 服务 | 镜像 | 宿主端口 | 职责 |
|---|---|---|---|
| `searxng` | `searxng/searxng:latest` | `127.0.0.1:8201` → 8080 | 元搜索引擎，聚合多引擎；挂载自建 `settings.yml`（`formats:[html,json]`） |
| `search-api` | 自建 `services/websearch/Dockerfile`（python:3.12-slim + uv） | `127.0.0.1:8204` → 8200 | 流水线编排 + MCP Server（`/mcp`）+ REST（`/search` `/fetch` `/health` `/metrics`）+ SQLite 缓存 |
| `reranker` | 自建 `services/websearch/reranker/Dockerfile`（torch CPU + transformers） | `127.0.0.1:8202` → 8000 | `POST /rerank`、`GET /health`；`BAAI/bge-reranker-v2-m3` 常驻，命名卷 `reranker_models` 缓存模型 |
| `crawler` | `unclecode/crawl4ai:latest` | `127.0.0.1:8203` → 11235 | `/md` 抓正文为 markdown（playwright/chromium 预装），抽取升级路径 |

- **所有端口只绑 `127.0.0.1`**：SearXNG 无鉴权、Crawl4AI 只有一个静态 token，绝不能对外暴露。
- 容器间用 service name 互访：`http://searxng:8080` / `http://reranker:8000` / `http://crawler:11235`。
- 模型下载走 `HF_ENDPOINT=https://hf-mirror.com`（国内默认镜像，可覆盖）。
- 缓存 bind mount 到 `services/websearch/data/`（已 gitignore）。
- **宿主端口默认 8204 而非 8200**：部分开发机上 8200 被 Logitech G Hub 的 LSGTransmit 长期占用，且它 accept 连接却从不响应——OrbStack 遇到端口被占会**静默跳过发布**，表现为「容器 healthy 但宿主 curl 超时」，极难查。可用 `SEARCH_API_PORT` 覆盖。
- `depends_on` + healthcheck：`search-api` **只硬依赖 searxng**（召回的唯一来源）；reranker/crawler 刻意不列入依赖——它们不可用时流水线要能**降级启动**，而不是被 compose 挡在门外。

### 分级可用（降级是设计的一部分，不是故障）

任何一层挂掉都退回上一层结果并**如实标记**（不静默、不抛异常、不让整条查询失败）。标记最终汇总到输出的 `meta:` 行与 `degraded=` 字段（见 §5）。

| 缺失/异常 | 行为 | 输出标记 |
|---|---|---|
| reranker 不可达/超时 | 跳过精排，沿用 RRF 序的 top-N | `rerank=unavailable` + `degraded=rerank_unavailable` |
| reranker 未配置（URL 空） | 同上，但属主动关闭 | `rerank=skipped` |
| crawler 不可达 | trafilatura 快路照抽；只有 trafilatura **也**失败才退引擎摘要 | `extract=DONE/TRIED:snippets_only` + `degraded=extract_snippets_only` |
| 部分抽取失败 | 抽到几篇算几篇 | `extract=1/3:partial` + `degraded=extract_partial` |
| 部分引擎无响应 | 该路照常融合，记录清单 | `unresponsive=e1,e2,...` |
| 召回路数偏少 | 正常融合，但降级计数 | `degraded=partial_routes` |
| searxng 全挂 | 返回明确不可用文案（不抛异常，Agent run 不崩） | `available=false` |
| 全链路超 25s | 返回已完成阶段的部分结果 | `degraded=hard_timeout` |

> **注意实现与计划的措辞差异**：计划草案里写「缺 reranker → `rerank: skipped`」，实际实现区分得更细——**主动未配置**才叫 `skipped`，**配置了但连不上**叫 `unavailable`（都降级到 RRF 序，但排障时能一眼分清是「没配」还是「挂了」）。消融关闭精排阶段则是 `ablated`。

## 3. 五级质量漏斗：每层做什么、怎么量

### 3.1 查询理解（`understand.py`）— 一次意图 → 最多 4 路互补检索式

规则化、确定性、零成本（默认不叫 LLM）。同一 query 恒定产出同一组路（可复现，评测前提）。

| 路 | 检索式 | 权重 | 触发条件 |
|---|---|---|---|
| `original` | 原查询整句 | 1.0 | 恒定；时效命中时类目加 `news` |
| `phrase` | 显著短语加引号 + 剩余关键词 | 0.9 | 能挑出 ≥3 字的显著短语（模型名/版本号/最长中文串优先），且与原句**不同构** |
| `keyword` | jieba `cut_for_search` 去停用词/单字虚词，保序去重 | 0.8 | 关键词 ≥2 个且与原句不同 |
| `extra` | **三选一互斥**：时效路（`news`）/ 英文实体路（中英混查捞英文原始资料，tech 时加 `it` 类目）/ 技术类目路（`it`：github/stackoverflow/hackernews/mdn） | 0.7 | 前 3 路未满 4 路时，用当前查询最缺的那种互补性 |

- **退化保护**：当查询本身就是一个引号短语（如 `"vector database"`），phrase 路会与 original 完全同构 → 不加。否则 RRF 会给同一份排名投两票（1.0 + 0.9），让 original 路凭空拿到双倍票权。
- **时效意图**：`今天/本周/最新/近期/今年/进展/新闻…` → SearXNG `time_range=day|week|month`，并据此走短缓存 TTL。
- **常青意图**：`文档/手册/教程/规范/是什么/什么是/API/SDK/参数…` → 走长缓存 TTL（技术文档类定义不随时间变）。
- **技术意图**：`api/sdk/github/docker/python/报错/配置/版本…` → extra 路追加 SearXNG `it` 类目。实测同一句 `transformer attention is all you need`：`general` 只 31 条、`it` 有 85 条——这是免费的召回上限抬升。
- `jieba` 为服务内依赖（隔离区，不入核心白名单）；中文分词粒度差异正是 keyword 路互补收益的来源。

### 3.2 召回（`recall.py`）— SearXNG 并发多路

- 每路一次 SearXNG 调用（`format=json`、`pageno=1..2`、`categories=general`（时效路加 `news`、技术路加 `it`）、`safesearch=0`），SearXNG 内部已聚合多引擎。
- 并发 `asyncio.gather`，单路超时 8s、召回总预算 10s；**单路失败不影响整体**，记入 `route_errors` 并把无响应引擎汇入 `unresponsive_engines`。
- 每路产出一个**有序列表**——这是 RRF 与 `route_agreement` 的输入。
- 度量：`recall@50`（50 候选窗口内是否存在 ≥1 个标注相关项），基线 live 观测每查询原始召回均值 ~13569/170 ≈ 80 条。

### 3.3 融合（`normalize.py` + `fuse.py`）— URL 归一化 + 加权 RRF

**URL 归一化**：小写 host、去 fragment、去 `utm_*`/`fbclid` 等跟踪参数、去尾斜杠、剥 `google.com/url?q=` 包装、`http→https`、合并 `m.`/`mobile.` 前缀。

**加权 RRF**（只用排名，不做量纲假设）：

```
score(d) = Σ_r  w_r / (k + rank_r(d))        k = 60
```

`rank_r(d)` 是文档 d 在第 r 路的排名（从 1 起），`w_r` 是该路权重（见 §3.1）。k=60 是 RRF 的经典默认值：k 越小越强调各路的头部，k 越大越平滑。

**近重复合并**：同归一化标题 + 同 host 路径前缀 → 保留最高分项。输出候选窗口 **top 50**（`candidate_window`）。

度量：`route_agreement` = top10 中出现在 ≥2 路的 URL 占比——一个**无需人工标注**的结构指标，反映多路的共识度。

### 3.4 重排（`rerank.py` + `reranker/`）— cross-encoder 精排 50→10

- 单次批量请求 reranker：`(query, title + snippet + url 路径语义化文本) × rerank_candidates`，取 **top `rerank_top_n`（10）**。
- reranker 侧：`BAAI/bge-reranker-v2-m3`、`torch.inference_mode()`、`torch.set_num_threads(min(8, cpu))`、启动预热一次、`asyncio.Semaphore(1)` 串行推理（CPU 上并发推理只会互相拖慢）。
- **成本模型**：CPU 上 cross-encoder 成本 ≈ `pairs × tokens²`。实测（arm64 / 10 核 / batch=8）：128 token ≈ 0.18s/对、251 token ≈ 0.53s/对、50 对 × 512 token = 44s——**长度是延迟的头号旋钮**。所以 `max_length` 按层分别下发（文档级窄 128、片段级宽 256），服务端 cap 512。
- **低置信丢弃**：低于 `rerank_score_threshold`（0.05）的候选直接丢，**不凑满 top10**——实测某一路会召回精排 0.0000 分的无关页，凑数只会污染输出。全丢时返回 0 条并附「为何」（见 §5 降级话术）。
- 客户端超时由编排层按硬超时剩余时间下发；失败/超时 → 回退 RRF 序并标 `rerank=unavailable`（**永不因精排失败而整条查询失败**）。
- 度量：`nDCG@10`（分级相关 2/1/0）、`MRR`（首个相关项倒数排名）、`rerank_shift`（精排后 top10 相对 RRF 序的位次变化量——重排到底做了多少事，可观测）。

### 3.5 抽取 + 片段级二次精排（`extract.py` + `chunk.py`）

- 对 top10 中的**前 `extract_top_n`（3）篇**抽正文；并发抽取，单页 10s，抽取总预算 12s。
- **抽取分层**（`EXTRACTOR=auto`）：先走进程内 `trafilatura` + httpx 快路（无浏览器、亚秒级），当正文 <400 字符或被 403/JS 拦截时升级到 Crawl4AI `/md`。要 Crawl4AI 独占抽取改 `EXTRACTOR=crawl4ai`，要纯快路改 `EXTRACTOR=trafilatura`（三条路径都实现）。
- **切片**：段落感知递归切分，块 400 字符、overlap 60（与 `knowledge/chunker.py` 同思路，服务内独立实现）。
- **片段级二次精排**：`query × 该页所有片段`（取分数最高的 `passage_candidates`=4 个候选）→ 每篇只留分数最高且过 `passage_score_threshold`（0.3）的 **`passages_per_doc`（2）段**；阈值不过则退回该篇引擎摘要（不留空）。
- URL 正文缓存命中则跳过抓取。
- 度量：`span_hit_rate`（片段召回率）= 输出片段中含 ≥1 个金标 `answer_spans` 的查询占比——**标注无关的最可信回归信号**（不依赖 URL 是否被标注，只看答案文本有没有被顶出来）。

## 4. MCP 工具面（平台看到的契约）

能力名 `websearch` → 平台暴露名 `mcp__websearch__web_search`（`assembler.expand_capability` 的 `mcp__{server}__{tool}` 规则）。工具面刻意收敛到 **3 个**（`tool_budget` 默认 8，每个工具都占位）：

| 工具 | 参数 | 说明 |
|---|---|---|
| `web_search` | `query`(必)、`max_results`=8、`extract`=true、`freshness`=auto\|day\|week\|month\|any、`site`、`lang`、`max_chars`=6000 | 主入口，返回 LLM 可直接消费的排序去重结果 |
| `web_fetch` | `url`(必)、`question`、`max_chars`=4000 | 单页正文抽取 + 针对 `question` 的片段精选（模型想深挖某一条时用） |
| `search_meta` | 无 | 流水线自报：各组件可达性、模型是否加载、近 N 次延迟分位、缓存命中率、无响应引擎清单 |

- `risk_level=read`（无副作用，不触发确认门）。
- 工具 description 面向**语义命中**撰写（覆盖「联网搜索/网页搜索/查资料/最新信息/新闻/官方文档/外部资料」等表述），让 retriever 在相关任务下能召回它。
- **调试用的阶段消融开关只开在 REST（`?stages=recall,fusion` 或 `--ablate`），不进 MCP 工具面**——避免污染 Agent 的工具签名。

## 5. 输出契约

### 5.1 MCP 文本输出（`web_search`）

MCP 返回**文本**（平台只把 text 块拼给模型）：

```
网页搜索：BGE-Reranker-v2-m3 参数量与最大上下文长度（8 条）

1. BGE-Reranker-v2-m3 最大 Tokens 数是多少 · bge-model.com
   https://bge-model.com/... | bge-model.com | 2024-xx
   ▸ 片段一（≤passage_chars 字）
   ▸ 片段二
2. ...

meta: routes=4 recall=80 dedup=52 window=50 agreement=0.74 rerank=ok extract=3/3:ok cache=miss elapsed=12.1s chars=4324
```

`meta:` 行逐字段（**可观测性优先：每层做了什么、降级了没有，一眼看清**）：

| 字段 | 含义 |
|---|---|
| `routes=N` | 实际产出的检索式路数（1~4） |
| `recall=N` | 多路原始召回总条数（去重前） |
| `dedup=N` | 归一化 + 近重复合并后的条数 |
| `window=N` | 进入精排的候选窗口大小（≤50） |
| `agreement=X` | `route_agreement`，top10 中出现在 ≥2 路的占比 |
| `rerank=STATUS` | `ok` / `partial` / `unavailable`(降级到RRF序) / `skipped`(未配置) / `ablated`(消融关闭) |
| `extract=D/T:STATUS` | 抽到 D 篇 / 试了 T 篇，STATUS ∈ `ok`/`partial`/`snippets_only`/`disabled`；未启用抽取时为 `skipped` |
| `cache=hit\|miss` | query_cache 是否命中（命中则整条流水线短路） |
| `elapsed=Xs` | 全链路耗时 |
| `chars=N` | 输出字符数（自报，迭代到不动点——对外自报长度与实际不符就是说谎） |
| `unresponsive=…` | （可选）无响应引擎清单，最多列 5 个 |
| `dropped=N` | （可选）因预算截断被丢弃的结果条数 |
| `truncated=yes` | （可选）输出超 `max_chars` 被按序截断 |
| `degraded=reason1,reason2` | （可选）降级原因，逗号连接：`hard_timeout`/`pipeline_error`/`recall_empty`/`partial_routes`/`rerank_{status}`/`extract_{status}`/`extract_partial` |
| `errors=N` | （可选）错误条数（详情在 REST JSON 的 `errors[]`） |

### 5.2 预算与截断

- `max_chars` 默认 6000、硬上限 12000（`clamp_max_chars`：≤0 用默认，上限硬顶，下限保证至少装得下「一条结果 + meta 行」）。
- 超预算**按序截断**（保排序，不保数量）并标 `truncated=yes` + `dropped=N`。
- **第一条无论如何都要给**：「0 条」的输出与「没搜到」在模型看来没有区别，而这两件事必须分得清——前者是预算不够，后者是上游确实没结果。

### 5.3 降级话术（顺序就是优先级，模型往往只读第一句）

- **searxng 全挂**（`available=false`）：
  > 网页搜索暂不可用：{原因}（这是服务端如实降级，不是查询无结果；可稍后重试或换更具体的关键词）
- **召回被掐断**（有结果但出数引擎 ≤3）——**先说降级、再说结果**：
  > 网页搜索降级：只有 N 个引擎给出了结果（…），M 个搜索引擎无响应（…）——召回被掐断了。
  > 这**不等于**「网上没有这方面的资料」：请换个说法重试，或稍后再试（引擎挂起有退避期，通常 1~10 分钟自恢复）。
- **精排判定全不相关**（召回了但精排分数全低于阈值 → 0 条）：`errors[]` 里补上「召回 N 条候选，但精排分数全部低于阈值 0.05，判定为无相关结果」——不写的话模型无从判断是该换关键词，还是服务坏了。
- **正常无结果**（出数引擎充足但确实没匹配）：`未搜到与「{query}」相关的结果。`

### 5.4 REST JSON（`/search`）

返回同等信息的结构化 JSON（含每阶段耗时 `timings[]`、各路排名、精排分数、`stats`、`flags`、`errors[]`、`window[]`、`docs[]`），供评测与调试。阶段消融走 `?stages=` 或评测脚本的 `--ablate`。

stdlib `sqlite3`（零依赖、可 `sqlite3` CLI 直接查、跨重启保留），落 `services/websearch/data/`，三张表：

| 表 | key | TTL | 用途 |
|---|---|---|---|
| `query_cache` | 归一化(query + 影响结果的参数) | `freshness=any` 1h / `day\|week` 15min / 技术常青 7d | 整条流水线短路（命中直接返回，`cache=hit`） |

## 7. 引擎配置（实测驱动，不是拍脑袋）

`searxng/settings.yml` 的引擎启用集是**本机实测**的结果，不是计划里假设的 google/bing/ddg：

- **已启用**（本机稳定出数）：`sogou` `360search` `naver` `yandex` `yahoo` `yep` `mwmbl` `wikipedia`（`display_type: list` + infobox）`hackernews` `baidu` `quark` + news 引擎。
- **已禁用**（实测不可用或有害）：
  - `google` / `google cse`：本地/机房 IP 频繁 CAPTCHA。
  - `duckduckgo`：TLS 握手被掐。
  - `brave` / `mojeek` / `startpage` / `qwant`：限流或无响应。
  - **`bing`：最坑——它「活着」但中文查询返回大量无关垃圾页**，混进召回反而拉低质量，故显式禁用（`bing news` 保留）。
  - 图片/视频类引擎：与文本搜索无关。
- `formats: [html, json]`（**头号坑：不加 `json` 会直接 403**）、`limiter: false`、`suspended_times`（AccessDenied/TooManyRequests 退避 60s、Captcha 退避 600s）。
- `SEARXNG_ENGINES` 环境变量可覆盖引擎集，不用改文件重建。

**CAPTCHA 轮转是常态**：基线 upstream 快照里 `contributing`(11) 与 `unresponsive`(14) **有重叠**（`bing news`/`mwmbl`/`naver`/`quark`/`sogou`/`yep` 同时出现在两个列表）——同一引擎在不同轮次时通时断，这是公网搜索引擎对本地 IP 的正常退避行为，不是配置错误。因此上游健康守卫的判据刻意宽松：**仅当 contributing ≤ 2 才判 degraded**（早期用「≥4 unresponsive」会在 CAPTCHA 轮转常态下假阳）。

## 8. 评测体系与基线

### 8.1 金标集 `eval/queries.yaml`

26 条，覆盖 5 类意图切片（`fact` 事实型 / `fresh` 时效型 / `tech` 技术型 / `zh` 中文长尾 / `en` 英文实体），每条含分级相关标注（`grade: 2` 精确答案页 / `grade: 1` 窄域名兜底）与 `answer_spans`（唯一答案串，自动判定免人工标注）。

**标注纪律**：实现期逐条**实际打开候选 URL（走 `/fetch` 全文取证）确认其确实回答问题**后才写 `grade: 2`；无法逐条确认的只标 `domain` + `grade: 1`。

### 8.2 指标定义

| 指标 | 判定 | 层 |
|---|---|---|
| `recall@50` | 50 候选窗口内是否存在 ≥1 个 grade≥1 | 召回 |
| `route_agreement` | top10 中出现在 ≥2 路的占比 | 融合 |
| `nDCG@10` | 分级相关（2/1/0）标准 nDCG | 重排 |
| `MRR` | 首个 grade≥1 的倒数排名 | 重排 |
| `span_hit_rate`（片段召回率） | 输出片段中含 ≥1 个 `answer_spans` 的查询占比 | 抽取 |
| 命中率 | metrics 表累计 query_cache / url_cache 命中比 | 缓存 |
| `p50/p95 延迟`、输出字符数、成本（恒为 0） | 直读 | 全链路 |

### 8.3 基线（口径 B，2026-09-16 本机实测，26 条 / 22 条 stable）

四档**递增漏斗**（`--ablate X` = 关掉 X 及其之后的阶段；档名 = 被消融的阶段，标签 = 累进到该点的漏斗）：

| 档（消融） | 漏斗语义 | recall@50 | nDCG@10 | MRR | agreement | span_hit | p50 | p95 | window | chars |
|---|---|---|---|---|---|---|---|---|---|---|
| `fusion` | 单路召回 | 0.773 | 0.133 | 0.242 | — | 0.842 | 4494 | 6634 | 29.5 | 3021 |
| `rerank` | + 多路 RRF 融合 | **0.909** | 0.202 | **0.449** | 0.964 | 1.000 | 1940 | 5027 | **49.1** | 3107 |
| `extract` | + cross-encoder 精排 | 0.818 | 0.115 | 0.125 | 0.747 | 0.895 | 6369 | 9254 | 48.8 | 3174 |
| `none` | + 抽取与片段精排（全流水线） | 0.818 | 0.138 | 0.157 | 0.743 | **0.947** | 12074 | 17851 | 48.4 | 4324 |

`compare.py` 对自身基线 **exit 0**（门禁只卡 `nDCG@10` / `recall@50` 回归 >0.03；MRR/span/agreement/p95 仅报告不拦）。缓存探针：命中 100%、冷 6032ms → 热 0ms、**6032× 加速**。

### 8.4 怎么读这张表（口径警示 —— 这几点必须如实理解，否则会误判质量）

**① 最可信的结构性增益是 `fusion → rerank`（多路 RRF 融合）这一步**：

- 候选窗口 `window` 从 29.5 **跃升到 49.1**（多路互补把窗口填满），`recall@50` +0.136、`MRR` +0.207、`route_agreement` 从无从计算变成 0.964。
- 这是**同轮内可对照、不依赖标注 URL 是否可达**的增益，直接印证判断②「多路召回 + 融合收益 > 单路调参」。

**② `nDCG@10` 的绝对值（0.11~0.20）系统性偏低，是度量假象，不是排序缺陷**：

- 两个成因叠加：**(a) 金标集稀疏 + 多有效答案查询**——`ideal_dcg` 把每条标注当唯一理想位次，一个装满「有效但未标注」页面的 top-10，nDCG 会趋零；**(b) 引擎构成漂移**——标注是在 google/bing 时代做的，本机这些引擎已禁用，标注的**具体 URL 不可达**，只有宽 `domain` 标注能救 `recall`。
- **直接反证**：诊断脚本逐条打开 top-10，`tech-001`（BGE-Reranker）精排把「最大 Tokens 数是多少」精确答案页排 #1（reranker 打分 rr=0.9891）、官方 `bge-model.com` 排 #6、`modelscope.cn` 官方镜像排 #7——**全部高度相关**，但无一匹配金标标注的 huggingface-discussions/github-issue URL，于是 nDCG≈0.066。
- **结论**：`nDCG@10` **仅用于跨版本对比**（同一引擎构成、同一金标集下，改动前后比高低），**不可当排序质量的绝对判据**。要看排序好不好，看下面的 span_hit 和逐条诊断。

**③ 各档独立重查活网 → 档间 delta 含引擎漂移噪声**：

- 四档不是「同一批召回结果逐级加工」，而是**每档各自重新查一遍活网**。所以 `rerank → extract` 的 `recall@50` 从 0.909 掉到 0.818 **不是精排把结果弄丢了**——精排根本不动 `window`（窗口在 fusion 阶段就定了，两档 window 48.8≈49.1），这 0.09 是两轮之间引擎构成漂移的纯噪声。
- 因此：**跨档只看 `fusion → rerank` 这种「结构性」跃升**（窗口、agreement 这类由流水线机制决定的量），不要逐档解读 recall 的小幅涨跌。

**④ `span_hit=0.947` 是全流水线最可信的质量信号**：94.7% 的带标准答案串的查询，输出片段里命中了答案文本——这直接证明「抽取 + 片段级精排」把答案顶到了模型眼前，且**不依赖任何 URL 标注**。

**⑤ 分意图（`none` 档）**：

| 意图 | n | recall@50 | nDCG@10 | span_hit |
|---|---|---|---|---|
| `en` 英文实体 | 5 | 1.0 | 0.258 | 1.0 |
| `fact` 事实型 | 6 | 1.0 | 0.212 | 1.0 |
| `fresh` 时效型 | 4 | 0.75 | 0.153 | —（无 span 标注） |
| `tech` 技术型 | 7 | 0.857 | 0.053 | 0.857 |
| `zh` 中文长尾 | 4 | **0.25** | 0.025 | 1.0（仅 1 条 span） |

- `en`/`fact` 最强（recall 1.0）；`zh` 的 `recall@50=0.25` **偏弱**——根因是中文引擎（baidu/sogou/quark）CAPTCHA 轮转，部分轮次几乎全挂，属**上游可用性**问题而非流水线缺陷（且该档 span_hit 仍 1.0，说明只要召回到了，答案就能顶出来）。这是当前最需要改善的切片（见 §12）。

## 9. 参数调优指南（每个旋钮调什么病）

全部 env 驱动（`config.py`），改 `.env` 即生效、不用重建镜像。宿主变量经 `docker-compose.yml` 注入。

| 旋钮 | 默认 | 调大治什么 | 调小治什么 | 代价 |
|---|---|---|---|---|
| `RRF_K`（`rrf_k`） | 60 | 各路头部差异大、想平滑排名影响 | 想更强调各路 top 结果 | 无（纯数学） |
| 路权重 `weight_map` | original1.0/phrase0.9/keyword0.8/extra0.7 | 某一路总是更准 → 提它的权 | 某一路总引入噪声 → 降权 | 无 |
| `CANDIDATE_WINDOW` | 50 | recall@50 不满、正确答案在 50 名外 | 精排延迟高（窗口↑→精排对数↑） | 窗口直接影响精排成本 |
| `RERANK_CANDIDATES` | **20**（计划草案 50） | 正确答案在窗口 20~50 名之间、需精排捞回 | 全链路超时（CPU 上 50对×512token=44s 顶穿 25s） | **延迟头号旋钮**（成本≈pairs×tokens²） |
| `RERANK_DOC_MAX_LENGTH`（→容器内 `RERANK_MAX_LENGTH`） | **128**（服务端 cap 512） | 长标题/长 snippet 被截断丢信息 | 精排延迟高 | 成本随长度平方增长 |
| `PASSAGE_MAX_LENGTH` | **256**（cap 512） | 片段长、答案被截 | 片段级精排延迟高 | 同上 |
| `RERANK_SCORE_THRESHOLD` | 0.05 | 输出混进无关页（提高门槛丢低分） | 结果太少/空（降门槛多留） | 过高会误丢相关页 |
| `EXTRACT_TOP_N` | **3**（计划草案 5） | 需更多页抽正文供深挖 | 抽取总预算超时 | 抽取延迟（并发抽 N 篇） |
| `PASSAGE_CANDIDATES` | 4 | 长文档里答案位置分散 | 片段级精排成本 | 轻 |
| `PASSAGE_SCORE_THRESHOLD` | 0.3 | 片段混进无关段落 | 该篇无片段过阈→退引擎摘要 | 轻 |
| `PASSAGES_PER_DOC` | 2 | 每篇想给模型更多上下文 | 输出超 max_chars | 输出长度 |
| `CHUNK_SIZE`/`CHUNK_OVERLAP` | 400/60 | 答案跨段被切碎 | 片段太粗、噪声多 | 轻 |
| `MAX_CHARS_DEFAULT`/`_HARD_CAP` | 6000/12000 | 输出被截断、模型拿不到足够上下文 | 触发平台上下文压缩（24000 阈） | 直接影响会话历史预算 |
| `PIPELINE_HARD_TIMEOUT` | 25.0s | 全链路经常超时截断 | 探活被拖死（必须 <30s 冒烟上限、<180s 探活） | 硬约束，上调需谨慎 |
| `EXTRACTOR` | auto | — | — | `crawl4ai`（全走浏览器，慢）/`trafilatura`（纯快路，JS 页抽不到） |
| `ROUTE_LLM` | false | 复杂查询需 LLM 改写检索式 | — | 开启后失去零成本 + 结果不可复现 |
| `SEARXNG_ENGINES` | 空（用 settings.yml） | 某引擎本机可用但被禁 | 某引擎出垃圾 | 覆盖引擎集 |

> **与计划草案的实测偏离**（都是为落进 25s 硬超时而在本机 CPU 上实测调出来的，非拍脑袋）：`RERANK_CANDIDATES` 50→20、`EXTRACT_TOP_N` 5→3、`max_length` 分层下发 128（文档级）/256（片段级）而非统一 512。原因：arm64 / 10 核 CPU 上 cross-encoder 成本 ≈ pairs×tokens²，50对×512token 实测 44s 会直接顶穿硬超时。

### 10.2 `app/modules/capabilities/websearch_seed.py`（仿 `procurement_seed.py`）

- **不**被任何 Worker 的 `capabilities` 引用 → 按 `retriever._task_scope` 规则落「通用兜底档」，任何主任务下都可被检索到。

`test_info`（冒烟用例，`expected` 留空 = 只要求执行不报错，避免脆弱断言）：`search_meta`（空入参）+ `web_search`（`{"query":"什么是向量数据库","max_results":3,"extract":False}`）。第二条刻意关掉抽取：冒烟单用例上限 30s，冷启动抽取会顶到线上。

### 10.3 `app/modules/capabilities/mcp_client.py` 自愈修复（本次发现并修了**两个真 bug**）

**bug 1（计划已预见）——判死不摘除**：`_health_loop` 判死一个 Server 后只 `conn.close()`、**未从 `_conns` 摘除**；而 `rebuild()` 对已存在的 cap_id `continue` → 容器重启后该能力永久失联。修法：判死分支 `close()` 后 `self._conns.pop(cap_id, None)`；`_health_loop` 每轮末尾调 `await self.rebuild()`（幂等、只补缺失连接）→ 容器恢复后最多 60s 自愈。

**bug 2（DoD 8 实测才暴露，计划未预见）——`CancelledError` 打死健康循环**：

- **现象**：重启 search-api 后，live backend 日志显示健康循环正确检测到「3 consecutive failures」并标记 unhealthy，**但随后 `mcp-health` 任务整个死掉**（`CancelledError` traceback），websearch 只能靠进程重载（fresh pool）回来，而非自愈。
- **根因**：被拆掉的 streamablehttp session 在 `close()`/探活时会泄出 `CancelledError`。而 **`CancelledError` 是 `BaseException` 不是 `Exception`**，`_health_round` 的 `except Exception` **接不住它** → 循环崩溃 → 不再 `rebuild()` → 永久失联直到进程重启。
- **修法**：健康循环用**显式 `_stopping` 标志**（仅由 `stop()` 置位）区分「真关机」与「session 拆掉的伪取消」：后者当一次探活失败处理（循环存活），前者才 re-raise。`close()` 同样不再泄露 `CancelledError`。
- **走过的坑（留作教训）**：首版用 `Task.cancelling() > 0` 做判据——**错的**。anyio 的 cancel scope 底层用 `task.cancel()` 实现，会把 `Task.cancelling()` 括到 >0，于是 session 拆掉的取消被误读为真关机而 re-raise。单测里 fake conn **手动**抛 `CancelledError`（`cancelling()` 保持 0）所以能过，但真实场景依旧崩。最终只靠 anyio 从不触碰的 `_stopping` 标志。
- **验证**：同一进程（PID 不变、无重载）在 search-api 重启后 ~164s 自愈到 healthy（新 session）；+4 条回归单测（含一条专盯 `_shutting_down()` 在 `Task.cancelling()>0` 时仍为 `False`，防有人重新加回那个错判据）。

## 11. 运维与排障

### 11.1 启停

```bash
agentos search up       # 拉起 4 容器（= docker compose --profile search up -d），等 search-api /health 就绪
agentos search status   # 4 容器运行/健康状态
agentos search logs     # 跟随日志（--tail=100）
agentos search down     # 停止（用 stop + 显式服务名，不用 compose down：down 是项目级操作，会连带拆掉 db/parser 共用网络）
make search-up / search-eval / search-model   # 等价入口；search-model 预拉 reranker 模型（首次 2.2GB）
```

- `agentos start` **不**等搜索栈（缺失只提示一行，不影响默认启动路径）；`agentos status` 容器清单已含 4 个搜索容器（未起时用 `·` 而非 `✗` 表示可选未起）。
- **后端若已在运行，起搜索栈后需重启后端**（`agentos restart`）让 websearch 能力重新探活；或等 ≤60s 健康循环自愈。

### 11.2 排障表

| 症状 | 排查 |
|---|---|
| 容器 healthy 但宿主 `curl localhost:8204` 超时 | 端口被占（OrbStack 静默跳过发布）：`lsof -i:8204`；改 `SEARCH_API_PORT` 避开 |
| searxng 返回 403 | `settings.yml` 的 `formats` 未含 `json`（头号坑）；确认挂载生效 |
| 搜不到/结果很少 | `search_meta` 看 `contributing_engines`：≤ 2 则是上游被掐（CAPTCHA 轮转，1~10min 自恢）；输出会带「召回被掐断」降级话术，**不等于网上没资料** |
| 结果质量差/无关页多 | 看 `meta:` 行 `rerank=` 是否 `unavailable`（精排挂了→退回 RRF 序）；检查某引擎是否出垃圾（如 bing 中文）→ `SEARXNG_ENGINES` 排除 |
| 全链路超时/被截断 | `meta:` 带 `degraded=hard_timeout`；调小 `RERANK_CANDIDATES`/`EXTRACT_TOP_N`/`*_MAX_LENGTH`（§9） |
| 工具从列表消失 | 能力被探活摘除：`agentos search status` 确认 search-api healthy；等 ≤60s 自愈（已修 `CancelledError` 打死循环的 bug，§10.3）；仍不回来则 `agentos restart` |
| reranker `/health` 报 `loaded:false` | 模型未下完/下失败：`docker compose --profile search logs -f reranker`；确认 `HF_ENDPOINT` 可达（默认 hf-mirror.com）；`make search-model` 预拉 |
| crawler 端口不通 | `CRAWL4AI_API_TOKEN` 与 search-api 的 `CRAWLER_TOKEN` 必须成对：≥​0.9 未设 token 时只绑容器内 loopback，发布的端口是死的 |
| 抽取总是 `snippets_only` | trafilatura 与 crawl4ai **都**失败才这样；单看 crawler 是否可达（`EXTRACTOR=auto` 下 trafilatura 是快路，crawler 只是升级路径） |

| # | 局限/债务 | 影响 | 还债触发 |
