# 运维手册

个人 Agent 平台的日常运维参考：启动停止、备份恢复、故障排查。

## 1. 日常启停（agentos CLI）

全局命令 `agentos`（软链至 `~/.local/bin/agentos`，指向 `bin/agentos`）：

```bash
agentos start     # 基础容器（pgvector + docling-serve）→ 后端 :8000 → 前端 :5173
agentos stop      # 停前后端进程 + docker compose stop
agentos restart   # stop + start
agentos status    # 查看三组服务的运行状态
agentos logs      # 跟随查看后端/前端日志（logs/ 下）
```

可选的自建网页搜索栈（profile `search`，默认不起；详见 [docs/自建网页搜索服务.md](./自建网页搜索服务.md)）：

```bash
agentos search up      # 拉起 4 容器（searxng/search-api/reranker/crawler），等 search-api /health 就绪
agentos search status  # 4 容器运行/健康状态
agentos search logs    # 跟随搜索栈日志
agentos search down    # 停止搜索栈（不影响 db/parser）
```

> 起搜索栈后，若后端已在运行需 `agentos restart` 让 websearch 能力重新探活（或等 ≤60s 健康循环自愈）。

产物位置：日志与 pid 文件在项目 `logs/`（已 gitignore）。

## 2. 数据备份

### 2.1 自动备份（已配置 crontab）

每天 04:30 执行 `scripts/backup_db.sh`，产物写入项目 `backups/`（已 gitignore）：

- `agent_platform_YYYYMMDD_HHMMSS.sql.gz` — 数据库逻辑备份（pg_dump | gzip）
- `data_YYYYMMDD_HHMMSS.tar.gz` — `backend/data/`（知识库解析产物 markdown 正文，
  不在库里；恢复时缺它则知识库检索失效）

保留最近 14 份，超出自动轮转删除。日志：`logs/backup.log`。

手动触发 / 调整保留份数：

```bash
scripts/backup_db.sh        # 立即备份一份
scripts/backup_db.sh 7      # 保留 7 份
```

crontab 管理：`crontab -l` 查看，`crontab -e` 编辑。

### 2.2 恢复

```bash
# 1. 停后端（避免恢复期间有写入）
agentos stop

# 2. 恢复数据库（先建空库再导入；-c 丢弃恢复前残留连接）
docker exec -i agent-platform-db psql -U agent -d postgres \
  -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='agent_platform' AND pid<>pg_backend_pid();"
docker exec -i agent-platform-db dropdb -U agent agent_platform
docker exec -i agent-platform-db createdb -U agent agent_platform
gunzip -c backups/agent_platform_XXXXXXXX_XXXXXX.sql.gz | \
  docker exec -i agent-platform-db psql -U agent -d agent_platform

# 3. 恢复数据目录
tar -xzf backups/data_XXXXXXXX_XXXXXX.tar.gz -C backend/

# 4. 重启并验证
agentos start
curl -s localhost:8000/health
```

## 3. 故障排查

| 症状 | 排查 |
|---|---|
| `agentos start` 报 no configuration file provided | 从软链调用时路径解析失败；确认 `~/.local/bin/agentos` 指向仓库内 `bin/agentos` 且该文件未被移动 |
| 后端起不来 | `agentos logs` 看报错；常见：8000 被占用（`lsof -i:8000`）、数据库容器未就绪、`.env` 缺失 |
| 数据库连不上 | `docker ps` 确认 agent-platform-db 在运行；`docker exec agent-platform-db pg_isready -U agent` |
| 前端页面空白/接口 404 | 确认后端健康；浏览器控制台看是否跨域/路由问题；前端代理配置在 `frontend/vite.config.ts` |
| 模型调用失败 | run 详情（前端任务详情页或 `GET /api/v1/runs/{id}/events`）看 error 事件；常见：Kimi 凭据过期、上下文超限 |
| 知识库检索无结果 | 确认文档 status=ready；`backend/data/parse/{doc_id}.md` 存在；embedding 维度 1024 与 pgvector 列一致 |
| 定时任务不触发 | scheduler 的 timer 状态是否 enabled（paused 是主动暂停） |
| 网页搜索搜不到/结果很少 | `search_meta` 或 `/metrics` 看 `contributing_engines`：≤2 是上游被掐（CAPTCHA 轮转，1~10min 自恢）；输出会带「召回被掐断」降级话术，不等于网上没资料 |
| 网页搜索结果质量差/无关页多 | 看输出 `meta:` 行 `rerank=` 是否 `unavailable`（精排挂了退回 RRF 序）；某引擎出垃圾（如 bing 中文）用 `SEARXNG_ENGINES` 排除；详见搜索服务文档 §9 调优 |
| run 显示已超时但还在跑 | **先看 `active_ms` 而不是 `elapsed_ms`**：M9-b 起 `runs.deadline_at` 一次写入后只被暂停/等待顺延，执行段时长单独记在 `active_ms`。`elapsed_ms` 超 `timeout_seconds` 属预期（排队 + 等外部回调都算墙钟）；只有 `active_ms` 逼近上限才会真的被巡检判超时（见 §4A 查询） |
| run 卡在「等待外部系统」 | 看 `await_broker` 里 `status='waiting'` 的行：`deadline_at` 到点会被巡检自动落定（`expired` → 工具失败码 `await_expired`），不需要人工干预；确认外部系统是否持有 `callback_token` 并在回调地址上重试；确需放弃用 `POST /api/v1/awaits/{id}/cancel`（等价于置 `cancelled` 并让 run 以 `await_cancelled` 继续） |
| 工具"返回成功但结果是失败文案" | 属于历史"假完成"缺陷，M9-b/P0-3 已封死：工具失败一律是 `{"ok": false, "error": {"code": …}}`。查 `runs.error.code` 或 `tool_result` 事件 payload 的 `error.code`，9 个码固定在 `engine/tool_outcome.py: TOOL_FAILURE_CODES`（自由文本只在 `detail`）/`source` 四值 `builtin`/`mcp`/`external`/`engine` |
| 模型说"我没有这个工具" | 用装配自检看事实：`GET /api/v1/capabilities/visibility`（或看 `capability_overflow` 事件）——M9-b/P0-2 起必得集**永不切片**，容量不足会显式报溢出而不是静默丢工具；真超物理上限（`MAX_TOOLS_HARD = 24`）会在注册/建 run 时直接拒绝 |
| `mcp__websearch__*` 工具从列表消失 | 能力被探活摘除：`agentos search status` 确认 search-api healthy；等 ≤60s 自愈（已修 `CancelledError` 打死健康循环的 bug）；仍不回来则 `agentos restart` |
| 任务卡/任务详情进度不动（但 run 还在跑） | M9-c/P1-5 起进度由**平台 watcher** 推（`settings.progress_watch_interval_seconds`，默认 5s）而不再靠模型：先确认 `progress` 事件在写（§4A 查询 6）——① 若**一条都没有**：多为该 run 没有子任务骨架（`progress_total = 0`，通用会话/纯工具 run 属正常不推）或 `tasks.conversation_id` 没挂上 run（无会话归属的 run 不推）；② 若有事件但前端不动：看前端是否在**重放/历史模式**（SSE 已结束的 run 不再实时推，只随历史查询重放）；③ watcher 只在**变化时**发，所以"没有新 `progress`"只代表数字没动，不代表 watcher 挂了；真怀疑 watcher 停了看进程日志里有没有 `engine-progress-watcher` 的异常栈（单轮异常只记日志、不退出，不会自愈成永久停摆，但连续报错说明库侧有问题）。排查见 §4A 查询 6 |
| 任务卡/任务详情出现「受阻支线」不知怎么处理 | M9-c/P1-6 起**不用再手工改 `task_steps`**：任务卡（或任务详情）该支线上直接给三动作——「关闭支线」= 收口为 `skipped`（可能让主任务随之收口）、「重新排队」= 退回 `pending` 重跑、「转人工」= 保持 `blocked` 并标记 `escalated`。动作统一落 `resolution.reason='manual'` + `converged_at`，并在**该支线所属 run** 的事件流里留 `unblocked`/`blocked` 痕迹（无 run 归属的支线只落状态）。排查见 §4A 查询 5 |

### 4A. 常用排查查询（M9-b 起）

```bash
docker exec -i agent-platform-db psql -U agent -d agent_platform
```

```sql
-- 1) 时长账本：墙钟 vs 执行时长（"超时"判定只看 active_ms 与 deadline_at）
SELECT id, status, started_at, deadline_at, active_ms, paused_at
FROM runs WHERE status IN ('running','paused_awaiting_confirm','waiting_external')
ORDER BY started_at;

-- 2) 外部等待：谁在等、等多久、何时到点
SELECT id, run_id, tool_name, status, created_at, deadline_at, waited_ms, error->>'code' AS code
FROM await_broker ORDER BY created_at DESC LIMIT 20;

-- 3) 结果产物：某 run 产出了什么（正文在 inline 行的 payload 里）
SELECT id, run_id, kind, name, size, storage, file_id, created_at
FROM run_artifacts ORDER BY created_at DESC LIMIT 20;

-- 3b) 产物取件排查（P2-1）：某次外部等待，外部服务到底能取到哪些文件
SELECT a.id AS await_id, a.status, a.callback_token, fa.file_id, fa.name, fa.kind, fa.storage
FROM await_broker a
LEFT JOIN run_artifacts fa ON fa.run_id = a.run_id
WHERE a.id = '<await_id>';

-- 4) 失败码分布：近 7 天哪类失败最多（"假完成"类问题按 code 归类）
SELECT payload->'error'->>'code' AS code, count(*)
FROM run_events
WHERE event_type = 'tool_result' AND created_at > now() - interval '7 days'
GROUP BY 1 ORDER BY 2 DESC;
```

> 停表语义提示：`waiting_external` / `paused_awaiting_confirm` 期间 `active_ms` **不增长**，
> 恢复时按 `paused_at` 计算 deadline 顺延——所以"等待 3 天"不会吃掉 run 的执行预算。
>
> 产物取件排查（P2-1）：取件授权范围 = 该 `await_id` 所属 run 的
> `run_artifacts.file_id` ∪ `runs.input.attachment_ids`。外部服务带 `X-API-Key` +
> `X-Callback-Token: <callback_token>` 取件：**403** = token 与 `await_id` 不匹配（或没带头），
> **404** = 文件不属于该 run / 文件不存在 / 产物正文不在盘上——接口**刻意不区分这三种 404**（避免越权探测），
> 所以排查时先用上面 3b 确认真有这行产物再报障；单文件超 `open_file_max_bytes`（默认 20MB）是 **413**。
> 端点与请求头见《第三方 Worker 开发与注册规范》§2.6.1。

```sql
-- 5) 受阻支线：还有多少条卡着、原因是什么（P1-6 起原因走枚举，不再靠自由文本后缀）
SELECT ts.status, ts.resolution->>'reason' AS reason, ts.resolution->>'action' AS action, count(*)
FROM task_steps ts
WHERE ts.status = 'blocked' OR ts.resolution->>'reason' IS NOT NULL
GROUP BY 1, 2, 3 ORDER BY 4 DESC;
```

> 收敛动作的"谁做的、什么时候"在 `task_steps.resolution` 里（`reason` / `action` / `detail` /
> `at` / `converged_at`），"发生过什么"在 `run_events` 的 `blocked` / `unblocked` 事件里。
> 原因枚举固定为 `run_ended` / `deadline_exceeded` / `user_cancelled` / `manual`（`manual` = 前台收敛）。

```sql
-- 6) 推送式进度（P1-5）：某 run 的进度事件时间线 + 是否与任务卡数字一致
SELECT e.seq, e.created_at, e.payload->>'done' AS done, e.payload->>'total' AS total,
       e.payload->>'label' AS label, t.progress_done AS task_done, t.progress_total AS task_total
FROM run_events e
LEFT JOIN tasks t ON t.conversation_id = (SELECT conversation_id FROM runs WHERE id = e.run_id)
WHERE e.run_id = '<run_id>' AND e.event_type = 'progress'
ORDER BY e.seq;
```

> 口径保证：`progress` 事件的数字**直读 `tasks.progress_done/total`**（不是 watcher 自己算的），
> 所以 `done=/total=` 与 `task_done/task_total` **必然相等**——不相等即为 bug（事件与看板分裂），报障时把这两列一起贴。
> `label` 为空串表示没有活跃子任务（前端只显示数字）；等外部回调时 `label` 是「等待外部回调」这类**阶段文案**，
> 数字可能长时间停在同一个值——这是设计意图（进度归平台，等待期模型不在场）。

### 4B. 可观测性三视图（P2-6 起）

三张**只读**视图：一是"现在跑一条要多久"（容量/排队决策的唯一依据），二是"外部等待全貌"（含巡检是否跟得上），
三是"失败到底失败在哪一层"（run 级结论，与视图 4 的工具级失败互补）。纯 SQL 交付，**无代码变更、不写库**。

```sql
-- 7) 运行时长分布：近 14 天按天的 P50/P95（elapsed = 墙钟含等待，active = 执行时长，单位 ms）
SELECT date_trunc('day', r.started_at)::date AS day,
       count(*) AS runs,
       round(percentile_cont(0.5) WITHIN GROUP (
           ORDER BY (r.result->'metrics'->>'elapsed_ms')::numeric))::bigint AS elapsed_p50_ms,
       round(percentile_cont(0.95) WITHIN GROUP (
           ORDER BY (r.result->'metrics'->>'elapsed_ms')::numeric))::bigint AS elapsed_p95_ms,
       round(percentile_cont(0.5) WITHIN GROUP (
           ORDER BY (r.result->'metrics'->>'active_ms')::numeric))::bigint AS active_p50_ms,
       round(percentile_cont(0.95) WITHIN GROUP (
           ORDER BY (r.result->'metrics'->>'active_ms')::numeric))::bigint AS active_p95_ms
FROM runs r
WHERE r.result->'metrics'->>'elapsed_ms' IS NOT NULL
  AND r.started_at > now() - interval '14 days'
GROUP BY 1 ORDER BY day DESC;
```

```sql
-- 8) 等待全貌：按 状态 × 工具 汇总外部等待（P0-4 一等化等待）
SELECT a.status,
       a.tool_name,
       count(*) AS awaits,
       round(avg(EXTRACT(epoch FROM (now() - a.created_at))))::bigint AS age_avg_s,
       round(coalesce(avg(a.waited_ms), 0) / 1000.0)::bigint AS waited_avg_s,
       count(*) FILTER (
           WHERE a.status = 'waiting' AND a.deadline_at < now()) AS overdue,
       count(*) FILTER (
           WHERE a.status = 'waiting'
             AND a.deadline_at >= now()
             AND a.deadline_at < now() + interval '1 hour') AS due_within_1h
FROM await_broker a
WHERE a.status = 'waiting' OR a.created_at > now() - interval '7 days'
GROUP BY a.status, a.tool_name ORDER BY awaits DESC, due_within_1h DESC;
```

> `overdue > 0` = **有等待过了点还没被翻成 `expired`**：巡检每 `await_sweep_interval_seconds`（默认 15s）扫一次，
> 正常情况下超时行最多滞后一个周期；持续 > 0 说明引擎巡检任务没在跑（或卡住），此时 run 会一直挂在
> `waiting_external`——**这是告警项，不是业务现象**。`due_within_1h` 是运维余量：这一小时内会有一批超时，
> 如果业务上本应回传，现在就是提醒外部服务的时间点。

```sql
-- 9) 失败码分布（run 级）：近 30 天 天 × code × phase（P0-3 起 error 是结构化对象）
SELECT date_trunc('day', r.finished_at)::date AS day,
       r.error->>'code' AS code,
       r.error->>'phase' AS phase,
       bool_or((r.error->>'retryable')::boolean) AS any_retryable,
       count(*) AS runs
FROM runs r
WHERE r.status = 'failed' AND r.finished_at > now() - interval '30 days'
GROUP BY 1, 2, 3 ORDER BY day DESC, runs DESC;
```

> 三视图口径提示（同一套解释，别按直觉读）：
>
> 1. **`runs` 表没有 `elapsed_ms` 列**。`elapsed_ms` / `active_ms` 都在 `runs.result->'metrics'` 里（P0-1 结果信封，
>    `schema` = `run_result/v0|v1`）。**v1.6 之前的存量 run 没有 `metrics` 键**——视图 7 的 `WHERE` 会把它们排除，
>    这是"口径从 v1.6 起算"，不是丢数据；要看老数据请用视图 1 的 `started_at`/`active_ms`。
> 2. 视图 7 用 `started_at`、视图 9 用 `finished_at` 做时间轴：**跨天的长 run 在视图 7 里落在开始那天**（按开始时刻归集，
>    便于"某天的负载"口径），在视图 9 里落在结束那天（便于"某天的结论"口径）。
> 3. **视图 4 与视图 9 是两个层级**：视图 4 是工具级失败（`run_events` 里 `tool_result` 的 `error.code`），
>    一次 run 可以有很多次工具失败却最终成功（`retryable` 的自愈就是设计意图）；视图 9 是 run 级结论
>    （`runs.status = 'failed'` 时 `runs.error` 才有内容）。排查顺序：先看 9 定位"哪一类 run 在挂"，
>    再对具体 run 用视图 4 看是哪一步的工具失败拖垮了它。
> 4. 这三段 SQL 只做过**语法校验**（离线按 PostgreSQL 方言解析），**未在真实库上执行过**——
>    首次在现网跑时先 `EXPLAIN` 确认走索引（视图 7/9 扫 `runs` 的时间列，视图 8 扫 `await_broker.status` 的小表）。

## 5. 例行检查（建议每周）

1. `crontab -l` 在位；`ls backups/` 有当日备份且大小正常（数据库 ~几十 MB）
2. `df -h` 磁盘余量（备份+日志+解析产物会缓慢增长）
3. 前端发一条闲聊 + 一条知识库查询，确认延迟与回答正常（黄金任务集见设计方案 §13.3）
