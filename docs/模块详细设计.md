## 0. 主流程总览

所有模块在一条主流程上各就各位：

```
用户发消息 → conversations 落库 → 创建 run(pending) + NOTIFY
→ Engine inbox 消费 → intent_router 分流（新主任务判定 → 只回软提示，不建 run）
→ 读 agents 配置 + 读当前主任务（tasks 模块：任务卡 + 主线待办 + 进度）
→ discovery 按归属分层检索能力 → assembler 装配上下文
→ planner 生成计划(入库，优先采用主任务主线) → LangGraph 跑 ReAct 回环(工具经 capabilities 执行)
→ 支线触发(ask_user) → task_steps 置 awaiting_user → interrupt → 卡片答复 → 恢复（不新开会话、不新起图）
→ hooks 全程计量/审计/熔断 → verify 验证(不达标带反馈回环)
→ 确认点 interrupt → 前端卡片 → 用户确认 → 恢复执行
→ 完成 → 写 result → 通知路由 → skills_forge 异步复盘
```

## 1. Engine 服务

### 1.1 engine —— Loop 引擎

#### 1.1.1 LangGraph 图结构（graph.py）

节点固定七个：

```
START → intent_router → context_assembly → planner → agent ⇄ tools → verify → END
                                                     ↑______________|
                                                  （验证不达标带反馈回环，计数限 3 次）
```

| 节点 | 类型 | 职责 |
|---|---|---|
| `intent_router` | 轻量分类 | 规则 + 小模型兜底；闲聊 → 廉价模型单次调用后 END，跳过全部装配流程 |
| `context_assembly` | 确定性节点 | 调 discovery 装配上下文（见 §1.2.3） |
| `planner` | 确定性节点 | 生成计划写入 plans 表，State 只存 plan_ref（见计划外置） |
| `agent` | LLM 节点 | ReAct 思考，条件边判断有无 tool_calls |
| `tools` | 执行节点 | 经 capabilities 的 MCP/HTTP 通道执行工具调用 |
| `verify` | 独立验证 LLM | 评估任务是否达成；不达标带反馈回环（限 3 次） |

`context_assembly` 与 `planner` 额外挂任务架构（M7a）：装配时把当前主任务卡（目标 + 进度 + 子任务清单含已答复内容）拼进 `protected_context`（永不压缩）；planner 先读主任务的待办主线步骤，有则直接转成计划（`plans.items` 带 `step_id`），无主线才回退 LLM 自由规划。

**确认点（interrupt）埋两处**：
1. 任务单提交前（planner 之后）——实体抽取结果可能出错，必须人审
2. 高危工具调用前（tools 节点内检查 `risk_level` 为 write/dangerous）

**支线澄清（interrupt 的复用，M7a）**：`tools` 节点在派发前识别元工具 `ask_user`（澄清型，阻塞）/ `declare_subtask`（登记型，不阻塞）。前者先按 `(run_id, name)` 幂等登记/复用支线步骤并置 `awaiting_user`，再 `interrupt({"reason": "subtask_clarification", "step_id": …})`；用户经 `POST /runs/{id}/confirm {answer}` 答复 → 步骤置 `done` 且答复写入 `resolution` → 以 `ToolMessage` 继续主流程。**不引入子图、不引入 Swarm**——一个暂停语义只有一条代码路径，重放安全靠幂等键保证。

#### 1.1.2 State 定义（引擎的数据契约）

```python
class LoopState(TypedDict):
    messages: Annotated[list, add_messages]   # 可压缩区（对话与工具观察结果）
    protected_context: dict    # 人格/画像/活跃计划/平台记忆/当前主任务卡——永不压缩
    capability_cache: dict     # 本轮已装配的工具与技能，含来源(pinned/semantic)
    plan_ref: int              # plans 表外键——计划在库里，不在上下文
    budget_state: dict         # 已耗 token / 迭代数 / 循环检测计数
    confirmation: dict | None  # 待确认的参数包
```

#### 1.1.3 inbox 事件队列（inbox.py）

循环消费统一入口，事件四类：

| 事件 | 来源 | 处理 |
|---|---|---|
| `user_input` | conversations / scheduler | 创建或推进 run |
| `resume` / `abort` | runs 控制接口 | 从检查点恢复 / 取消执行 |
| `confirmation` | 确认卡片提交 | 恢复 interrupt 的图 |

- 实现：PG 事件表 + `LISTEN/NOTIFY` 即时唤醒 + 30s 轮询兜底（防丢通知）
- 广播事件：`capability_changed`（能力注册/变更时通知 Engine 重建连接池与检索池）
- 设计收益：**分叉、恢复、重放、二期拆进程，全部是队列操作，图本体不感知**

#### 1.1.4 生命周期钩子（hooks.py）

六个钩子位，横切逻辑全挂这里，图保持纯净：

```
on_run_start / on_run_end
on_turn_start / on_turn_end               # 计量 token、写 run_events
on_tool_call(pre) / on_tool_result(post)  # 审计、高危确认、循环检测、结构化错误包装
on_context_pressure                       # 触发 assembler 压缩
```

默认钩子链装配顺序：`audit → metering → budget → loop-detect`。预算熔断是钩子而非图节点。

#### 1.1.5 预算熔断（budget.py）

四道闸：

| 闸门 | 默认值 | 动作 |
|---|---|---|
| max_iterations | 25 | 触发即写 `budget_warning` 事件并优雅终止 |
| 单 run token 上限 | 按 Agent 配置 | 同上 |
| 同工具同参数连续调用 | 3 次 | 熔断，判定死循环 |
| 全局超时 | 按 Agent 配置 | 同上 |

终止后 run 状态置 `failed`，原因落库。

#### 1.1.6 检查点（checkpointer.py）

- `PostgresSaver` 直连主库，`thread_id = conversation_id`
- 断点恢复流程：inbox 消费到 `resume` → 读 run 的 checkpoint_ref → `graph.aget_state` 校验完整性 → 从中断超步继续

#### 1.1.7 事件生产（events.py）

- 三级事件（节点/工具/token）统一封装为九类：`message_delta` / `thought` / `tool_call` / `tool_result` / `plan_updated` / `confirmation_request` / `budget_warning` / `run_status` / `error`
- **任务架构不新增事件类型**：主任务/子任务进度变化复用 `plan_updated`（`items` 即子任务清单，带 `step_id`/`kind`，payload 另有 `task_id` 与 `progress`），支线澄清复用 `confirmation_request`（`reason=subtask_clarification`）。事件族冻结，旧前端忽略未知字段即可
- 写 `run_events` 表 + NOTIFY → API 读表转 SSE
- **Engine 不直接碰前端**

### 1.2 discovery —— 能力发现与装配

#### 1.2.1 indexer

能力注册/变更时，把 `name + description + 工具签名摘要` 拼文本 → embedding → 回写 capabilities 表向量列。与知识库共用同一套 embedding 管道。

#### 1.2.2 retriever

- 输入：用户任务文本 + 会话近几轮摘要
- 输出：Top-K 能力（K 默认 8，受 Agent 的 `tool_budget` 约束）
- 检索池：enabled 且健康的能力 ∪ Agent pinned 集合（去重）
- **归属分层（M7a，ADR-28）**：传入 `task_id` 时先按归属把候选分三层——`task_domain`（本主任务域）/ `task_common`（通用任务集）/ `global`（其它域）——再按层序重排后截断 Top-K；候选先放大 `k × 3` 再重排，避免"分层把好能力挤出预算"。层内保持语义距离序；当前主线步骤的 `capability_hint` 命中的能力在本层内提权。不给 `task_id`（旧调用/定时任务）时行为与 M7a 前完全一致
- 每个命中能力带 `scope` 标记，透传到装配层写入工具条目的 `source`（便于审计"这个工具为什么被装配进来"）
- 同时暴露为内置元工具 `search_more_tools`（同样接受 `task_id`）——**检索本身工具化**，Agent 觉得工具不够可自行翻找

#### 1.2.3 assembler（核心）

上下文 = 五个区，按预算分配：

```
[protected_context 固定区]  人格 / 画像 / 平台记忆 / 活跃计划
[技能元数据区]              ~100 token/技能（渐进披露，全文按 load_skill 拉取）
[工具描述区]                受 tool_budget 封顶（pinned + semantic Top-K）
[历史消息区]                动态（压缩对象）
[计划状态区]                每轮注入最新 todo 状态
```

两级压缩，触发条件 = 上下文使用率 ≥ 80%：

| 级别 | 动作 |
|---|---|
| L1 | 最旧 N 轮工具观察结果折叠为一行摘要（`tool_result` → "已执行 X，结果：…"） |
| L2 | 全量历史摘要重启（保留首尾，中间压缩成段），发 `context_compacted` 事件供审计 |

**保护名单（永不压缩）**：protected_context、活跃计划、当前工具描述。

### 1.3 capabilities —— 能力注册与供给

#### 1.3.1 统一 payload 结构（一张表，type 决定解释）

| type | payload 内容 |
|---|---|
| `tool` | Python 函数引用 / 签名 JSON Schema |
| `skill` | SKILL.md 全文（yaml 头 name/description/version + 正文方法论） |
| `mcp` | transport(stdio/http)、launch 命令、env（密钥加密）、**tools 开关清单** |
| `plugin` | 同 mcp（插件 = 自研 MCP Server） |

#### 1.3.2 注册流程（管理侧，API 服务执行）

```
提交元数据 → 规范校验（yaml 头完整性 / launch 可解析）
→ 冒烟测试：临时拉起连接，逐条跑 test_info
   ├─ tool：调函数，比对返回值
   ├─ mcp：list_tools + 各启用工具试调用
   └─ skill：格式校验 + 引用脚本存在性
→ 通过才 enabled；失败退回并附错误报告
→ 触发 indexer → 广播 capability_changed
```

#### 1.3.3 运行侧供给（mcp_client.py，Engine 服务）

- 应用启动时按注册表拉起 enabled 的 stdio Server / 建立 http 连接，维护**连接池**（每 Server 一条会话，工具调用串行排队）
- 健康检查：每 60s `ping/list_tools`，连续 3 次失败标记 unhealthy 并从检索池摘除
- 热注册：收到 `capability_changed` 事件后重建连接池与检索池，不重启进程
- **工具开关两级生效**：capability 级（整个 Server/技能停用）+ tool 级（Server 内只暴露启用的工具）——上下文膨胀的最后闸门

#### 1.3.4 高危标记

capability 带 `risk_level(read/write/dangerous)`；`write/dangerous` 的工具调用触发确认点。

### 1.4 skills_forge —— 技能沉淀闭环

| 阶段 | 做法 |
|---|---|
| 触发 | hooks.on_run_end 挂接：run 为 done 且迭代数 ≥ 3（太简单不值得沉淀）；异步发起，不阻塞结果返回 |
| 复盘 | 独立 LLM 调用；输入 = 任务描述 + run_events 提炼的执行轨迹摘要；三问：方法可复用吗？已有 Skill 覆盖吗（检索比对）？写成 SKILL.md 草稿 |
| 去重 | 与现有技能库 embedding 相似度 > 0.9 → 改为生成"修订建议"而非新草稿 |
| 纠错沉淀 | 用户在确认卡片改过参数 / 驳回过结果的 run 同样触发复盘——把"别这么做"写进草稿的注意事项区 |
| 人审入库 | 草稿进 skill_proposals(proposed) → 前端审核 → approve 后写 capabilities(type=skill) → indexer 自动进检索池 → 下次同类任务被语义发现命中 |

### 1.5 scheduler —— 触发器

APScheduler（AsyncIOScheduler）；**timers/alarms 表为唯一事实源，进程重启全量重载**。

| Job | 触发 | 动作 |
|---|---|---|
| timer | cron 到点 | input_template 实例化 → 创建 run(pending, trigger=scheduled) + NOTIFY——与手动触发同一条路 |
| alarm | 绝对时间到点 | 写通知事件（纯提醒，不建 run） |
| memory_consolidation | 每日 03:00 | 见 §2.6 |

### 1.6 tasks —— 主任务与子任务（M7a）

四层架构的唯一实现处（L1 定义层 → L2 实例层 → L3 归属层 → L4 会话层）。**依赖方向单向**：engine 经 EngineBackend 协议读/写任务状态（见 1.6.1），tasks 只读写自己的表，绝不反向调用 engine（不 import graph/runtime），也不发 SSE。

| 层 | 实体 | 谁写 |
|---|---|---|
| L1 定义层 | 文件包 `data/workers/<名>/<版本>/`（WORKER.md + sub_workers/，registry mtime 缓存直读） | 只由人经 `/workers` API 或直接编辑文件维护；LLM 无写入口；只有生效版本可编辑，历史版本只读 |
| L2 实例层 | `tasks` / `task_steps` | 创建任务时按 worker + 版本从文件实例化（`worker_name`/`worker_version` 创建时锁定，`worker_step_ref` 回指 sub_workers 文件夹名）；运行期由 engine 经服务函数更新状态 |
| L3 归属层 | 主 WORKER.md 头 `capabilities:` 工具引用清单 | 只由人维护（`GET /workers/{name}/capabilities` 实时校验命中/缺失） |
| L4 会话层 | `tasks.conversation_id` UNIQUE | 创建任务时建立 1:1 会话 |

#### 1.6.1 对外契约：EngineBackend 的任务钩子（engine 只用这些）

engine 不直接 import tasks 的 ORM/服务，而是经 `backend.py` 的 `EngineBackend` 协议（`backend_impl.py` 里转发到 `tasks.service`）——与 MCP/知识库/模型的接法一致，保证二期拆进程时换实现即可。

| 钩子（EngineBackend） | 底层服务函数 | 用途 |
|---|---|---|
| `ensure_task_id(conversation_id) → task_id \| None` | `service.ensure_task_for_conversation` | 会话 → 主任务实例（1 会话 1 主任务；历史会话首次访问时自动挂靠「通用任务」；timer 无会话返回 None） |
| `get_task_context(task_id) → dict \| None` | `service.task_context` / `render_task_card` | 任务卡文本 + 子任务清单，装配时注入 protected 区 |
| `start_task_plan(task_id, run_id) → items \| None` | `service.plan_items_from_steps` / `advance_run_steps` | 主线步骤 → `plans.items`（带 `step_id`/`kind`）并把第一步置 `doing`；无待办主线返回 None（planner 回退自由规划） |
| `raise_subtask(task_id, run_id, name, description, question) → step` | `service.find_or_create_branch_step` / `raise_branch_step` | 幂等登记支线；`question` 非空即阻塞型澄清（run 将暂停等答复） |
| `answer_subtask(task_id, step_id, answer, run_id) → bool` | `service.answer_branch_step` | 答复回填 `resolution` + 置 `done` + 重算进度 |
| `finalize_task_plan(task_id, run_id, achieved) → int` | `service.finalize_task_plan` / `resolve_task_step` | run 终态回写：达成则推进绑定主步骤至 `done`，返回推进条数 |
| —（每轮状态变更时） | `service.emit_task_steps` | 子任务清单变化派发 `plan_updated`（不新增事件类型） |

模块内部能力（不经协议）：`get_worker_def`（文件源 Worker 定义入口，绑定版本缺目录时降级最新版本）、`worker_display`（含内建 `COMMON_WORKER` 通用任务常量，不落库）、`detect_task_switch`（新主任务判定，遍历启用 Worker 的 L1 元信息）、`rebind_worker`（无进度时重绑 Worker 并重建骨架）、`recompute_progress`（进度唯一入口）、`append_out_of_scope`（越界记录）、`sync_task_title`；看板聚合按 `worker_name` 从 tasks 行分组（Worker 文件缺失时兜底显示名称）。

#### 1.6.2 三条不变量

1. **进度只有一个来源**——`tasks.progress_done/progress_total` 由 `recompute_progress` 从 `task_steps` 重算。看板、任务卡、`plan_updated` 事件三处读同一份事实，任何一处都不许自己算。
2. **支线幂等**——支线步骤按 `(run_id, name)` 复用（LangGraph 恢复会整节点重放）；重复触发只把该行重置回 `awaiting_user`，不新增行。
3. **通用任务兜底**——内建常量 `COMMON_WORKER`（不落库、无文件）；未被任何启用 Worker 引用的能力自动落「通用任务」域；创建任务时若 Worker 不可用/旧会话无任务，一律回退到「通用任务」实例，保证 M7a 上线后旧路径不回归。

#### 1.6.3 新主任务判定（软提示）

同一会话中判定用户发起了**另一个**主任务时，不硬拦、不落消息、不建 run——只回一个 suggestion 卡片：

- 「新开会话」→ 创会话 + 新任务实例（走正常创建路径）
- 「仍在本会话继续」→ 写 `tasks.out_of_scope` 并落消息、继续本任务；任务卡追加"请专注当前主任务"提示，让模型知道本次越界

判定为轻量启发式 + 轻量模型（成本受控）；漏判时用户可手动「新建任务」，误判时用户可直接忽略——把架构决策权留给用户（债 9）。

## 2. API 服务

### 2.1 agents —— Agent 定义

Agent = 聚合配置：

```
人格（soul_md / identity_md / memory_md 三个可编辑 Markdown 字段）
+ 模型绑定（model_provider_id）
+ 能力策略（capability_bindings：pinned 显式绑定 / semantic 参与语义发现）
+ 预算（tool_budget、token 上限）
```

- 人格三件套是普通 Markdown 字段，前端编辑器直接改——个人平台不用文件夹结构，但保留"人格/身份/记忆"分离的字段组织
- 内置默认 Agent（首次启动 seed），平台最小可用状态 = 零配置
- 对 Engine 只提供 `get_agent_config(id)` 读模型；变更对下一个 run 生效，不影响进行中的 run

### 2.2 conversations —— 会话与消息

- **会话 = LangGraph thread**：conversations.id 即 checkpointer 的 thread_id，一一对应
- **会话与主任务实例 1:1**（ADR-26）：`tasks.conversation_id` 唯一。会话即任务档案——"新开会话"在语义上就等于"新开一个主任务"，看板可直接按会话聚合，也避免一个会话里混多件事导致上下文污染；历史会话（M7a 之前创建、无任务行）在读取时自动挂靠「通用任务」实例
- 发消息**不同步执行**：落 message → 创建 run → 返回 run_id，前端转 SSE 订阅——发消息接口永远快
- 会话切割：凌晨 3 点整理 Job 顺带关闭旧会话（status=closed），新对话自动新开
- messages.content 为 JSONB：`{text, tool_calls[], attachments[], token_usage}`——工具调用痕迹是消息流的一部分

### 2.3 runs（管理侧）—— 队列的对外视图

- 状态机：`pending → running → (paused_awaiting_confirm) → done | failed | cancelled`
- 查询面：按会话/状态/触发方式过滤；详情聚合 run_events 的执行轨迹
- **确认与支线答复同一条通道**：`POST /runs/{run_id}/confirm {answer}`（`answer` 非空，1~4000 字）→ inbox `confirmation` 事件 → 恢复 interrupt 的图。高危确认传结构化决策文本；支线澄清传用户自由文本答复——由 `interrupt` 的 `reason` 区分（`subtask_clarification`），runtime 对任何非空答复都恢复执行；`answer == "rejected"` 仍走技能沉淀的纠错复盘路径
- **任务相关字段**：run 详情附带 `task_id` / `step_id`（若有），前端据此把"这一轮属于哪个子任务"显示在任务条上
- 控制面：`resume / abort / confirm` 全部是**往 inbox 投事件**，管理侧不持有任何执行态——干预与输入同构
- SSE 端点：`GET /runs/{id}/events`；实时段 LISTEN 推送 + 历史段从 run_events 表补齐；断线重连用事件序号续传

### 2.4 knowledge —— 知识库管道

#### 2.4.1 管道（API 服务内 asyncio 后台任务，纯 I/O）

```
上传文件 → files 存储 → 调解析容器(REST: /parse) → markdown + 结构化元素
→ 切分（按结构，块 512±128 token，带标题路径元数据）
→ embedding 批量调用（8 并发）→ kb_chunks 入库（带 embedding_model + dim）
→ 文档状态 uploaded → parsing → chunking → embedding → ready | failed
```

- 每步失败可从断点重试（状态机驱动）
- **reindex**：换 embedding 模型后按库触发；标记旧向量组废弃，共存期间可回退

#### 2.4.2 检索工具（运行侧，Engine 调用）

`search_knowledge(query, kb_ids?)` → pgvector 余弦 Top-K + 结构元数据拼装为上下文片段；注册为普通 capability——**知识库对引擎只是个工具**。

### 2.5 models —— 模型接入与记账

- **Provider 抽象**：`LLMProvider.chat(messages, tools)` 与 `EmbeddingProvider.embed(texts)` 两个协议；实现类：OpenAI 兼容（覆盖 DeepSeek/Qwen/Kimi 等）+ Anthropic + Ollama
- 密钥：Fernet 对称加密落库，密钥来自 .env
- **记账**：engine 的 metering 钩子回调 `record_usage(provider_id, in_tokens, out_tokens)` → 内存聚合 → 每分钟批量 upsert `model_usage_daily`；日限额在 Provider 层强制（超限拒绝调用并通知）
- 模型变更：改 Agent 绑定，下一个 run 生效

### 2.6 memory —— 记忆体系

- 载体：`memory_files` 表（kind=platform 平台记忆 / kind=daily 日期记忆），content 为 Markdown + embedding
- **整理 Job（每日 03:00）**：读当日全部 runs + messages → LLM 提炼两份产物：
  1. 与用户无关的平台级要点 → 追加 platform 记忆
  2. 用户个人关键信息（偏好/纠正/事实）→ 写当日 daily 文件
  新内容 embedding 入库
- **注入**：assembler 的 protected 区固定注入 = platform 记忆全文 + 最近 2 天 daily 文件——每个新 run 自动携带"我是谁 + 最近发生了什么"
- 查询面：文件浏览 / 手动编辑接口（**个人平台红利：记忆可直接手改**）

### 2.7 tasks（管理侧）—— 任务实例与看板；Worker 定义归 workers 模块

- 路由分两块（定义层归 `workers` 模块、实例层归 `tasks` 模块，`api/v1` 只做汇总）：
  - **定义层（人工维护，`/workers`）**：`GET/POST /workers`（列表/新建脚手架+v1）、`GET/PATCH/DELETE /workers/{name}`（详情/启停与切生效版本/删除）、`POST /workers/{name}/versions`（**构建新版本**：复制生效版本目录 → vN+1；编辑文件不产生新版本）、`DELETE /workers/{name}/versions/{v}`（禁删生效版本/最后一个）、`GET /workers/{name}/tree?version=`（文件树）、`GET/PUT/POST/DELETE /workers/{name}/file?path=`（读写文件；只有生效版本可写，写时校验 yaml 头与 name 一致性，路径越界防护）、`POST /workers/{name}/sub-workers`（子任务脚手架）、`GET /workers/{name}/capabilities`（工具引用清单 ↔ capabilities 表校验，返回命中/缺失）
  - **实例层**：`POST /tasks`（传 `worker_name` + 首条消息 → 原子创建会话 + 任务实例（锁定当时生效版本）+ 步骤骨架，首条消息顺带建 run）、`GET /tasks`（平铺列表）+ `GET /tasks/board`（看板聚合：按 worker_name 从 tasks 行分组 + 进度 + 待确认角标 + 未读数，一次请求出整屏）、`GET /tasks/{id}`（任务详情：子任务清单 + 答复内容 + 关联 run）、`GET/PATCH /tasks/{id}/steps[/{step_id}]`（人工改状态/补子任务）
- **看板聚合独立于会话分页**：左栏不再是"会话流水"，而是任务看板；`board` 是唯一给列表用的接口，前端不 N+1 拉进度（债 11 留了物化视图/缓存接缝）
- 停用 Worker（manifest `enabled=false`）只影响新建任务入口与意图识别候选；历史实例与其任务卡不受影响——任务卡读创建时绑定版本的文件，绑定版本目录被删时降级最新可用版本并只显示名称骨架

### 2.8 files —— 文件存取

- 路径规范：`data/files/{YYYY-MM}/{uuid}{.ext}`；DB 记 `{id, path, mime, size, sha256, ref_type, ref_id}`
- sha256 去重（重复上传引用计数）
- ref 记录引用方（knowledge 文档 / 消息附件）；无引用孤儿文件由整理 Job 清理
- 上传接口统一走这里，knowledge 与消息附件复用

## 4. 模块间四条硬边界（防止设计腐化）

1. **Engine 不知道前端存在**——只写库和事件，谁来读不关心
2. **所有能力执行不发生在两个应用服务进程内**——经 capabilities 的 MCP/HTTP 通道出去
3. **模块间共享数据只经 PostgreSQL**——除 engine → discovery/capabilities 的进程内函数调用外，跨模块一律走库或事件，不允许私下建网络通道
4. **tasks 是纯生产者/记录者，不是引擎**——engine 单向调用 tasks 的服务函数读写任务状态；tasks 不 import graph/runtime、不触发 run、不直接发 SSE。任务状态的**唯一写入口是 tasks 模块**，engine 不直接写 `task_steps` 表（防止两条写路径把进度算歪）

## 5. 接口冻结优先级

复杂度最高的三处，开发前优先冻结接口签名：

1. **engine**：图结构 / LoopState / 钩子链协议
2. **discovery**：assembler 的装配输入输出与预算分配接口
3. **capabilities**：注册测试协议与 mcp_client 连接池接口
4. **tasks**：任务卡/计划项/子任务状态的读写契约（`task_context`、`plan_items_from_steps`、`raise_branch_step`/`answer_branch_step` 的幂等语义）与 `GET /tasks/board` 的聚合契约——前端只认这四个，内部表结构可自由演进
